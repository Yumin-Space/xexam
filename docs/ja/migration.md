# 移行とロールバック

> この文書では、すべてのアップグレード手順を新しい順に説明します：
>
> - **v0.7.5 または v0.7 → v0.8**（第 1 節）：AI サービス `ai-service` の入った新しい `docker-compose.yml`（3 つ目のイメージ `xexam-ai-service` と 2 つのボリューム）。データベースはスキーマ v5 に自動で移行します。移行の前に、バックアップのコピーが書き出されます。AI は管理者が設定するまでオフのままです。
> - **v0.6 → v0.8**（第 2 節）：データベースはスキーマ v5 と WAL モードに自動で移行します。移行の前に、バックアップのコピーが書き出されます。その後、古い 3 列・4 列の Excel 形式の問題が出題停止になるので、6 列形式のワークブックで問題集を更新します。
> - **v0.5 または v0.5.1 → v0.8**（第 3 節）：ログインとその後のスキーマが、一度に加わります。
> - **v0.4 → v0.5 以降**（第 4 節）：問題集、試験の詳細、設定（スキーマ v2）。現在は、その後のすべてと一緒に行われます。
> - **Python 版 v0.2.x → Rust + TypeScript + Nginx 版（v0.3）**（第 5〜11 節）：このときはデータベースファイルもスキーマも変わっていません。切り替えは「プログラムの入れ替え」であって「データの引っ越し」ではありませんでした。判断の根拠：[migration-plan.md](../zh-CN/history/migration-plan.md)。リスク：[risk-assessment.md](../zh-CN/history/risk-assessment.md)。
> - **v0.1 → それ以降**（第 12 節）：データベースのファイル名について。
>
> スキーマが変わるアップグレードでは、どれもまずデータベースのコピーを **1 つ** 書き出します。名前はそれまでのスキーマにちなんだもので、`xexam.db` と同じ場所の `backups/xexam-schema<N>-<YYYYmmdd-HHMMSS>.db` です（Docker では、ボリューム `xexam_data` 内の `/data/backups/`）。ロールバックとは、常に**そのコピーを元に戻し**、古いイメージを動かすことです。背景は [database.md](database.md) の第 6 節にあります。v0.8 の AI のデータベースは専用のボリュームにあり、メインのデータベースのロールバックで触れられることはありません。
>
> **v0.6 以前からのアップグレードでは、すべての問題が出題停止になります。** v0.7 からは 6 列形式の Excel しかインポートできず、起動のたびに、以前の版の 3 列・4 列形式から取り込んだ問題を出題停止にします。v0.6 以前の問題はどれも、そのどちらかの形式です。問題集、学習記録、統計は残ります。アップグレードの前に各ワークブックの 6 列形式の版を用意し（[usage.md](usage.md) の第 12 節）、アップグレードの後で、それで各問題集を更新してください（2.4 節）。

## 1. v0.7.5（または v0.7）から v0.8 へのアップグレード

### 1.1 何が変わるか

v0.8 では AI チャットが加わり、専用のデータベースを持つ **3 つ目のコンテナ** `ai-service`（イメージ `xexam-ai-service`）で動きます。そのために **新しい `docker-compose.yml`** が必要です：

| | v0.7.5 | v0.8 |
|---|---|---|
| イメージ | `xexam-frontend`、`xexam-backend` | 同じ 2 つに加えて **`xexam-ai-service`** |
| コンテナ（Compose のサービス） | `xexam-frontend`、`xexam-backend`（`frontend`、`backend`） | 同じ 2 つに加えて **`ai-service`**（`ai-service`） |
| ボリューム | `xexam_data` | `xexam_data`（変更なし）、**`xexam_ai_data`**（AI のデータベースとそのキーファイル）、**`xexam_link`**（バックエンドと AI サービスが共有するトークン `internal.token` だけ） |
| ネットワーク | `internal`（インターネットなし）、`public` | 同じものに加えて **`egress`**。`ai-service` だけの外向きのインターネット接続で、バックエンドは今も接続できません |

古い compose ファイルでも v0.8 は起動し、AI 以外はすべて動きます：AI チャットはメニューになく、**AI 設定** には ai-service が動いていないと表示され（新しい compose ファイルをダウンロードするようにというヒント付き）、バックエンドは `AI link off: cannot create /link/internal.token (…)` とログに出します。

**初めての起動** で、バックエンドはリクエストを受け付ける前に次の処理を行います：

1. **バックアップ。** データベースのコピーを `/data/backups/xexam-schema4-<YYYYmmdd-HHMMSS>.db` に書き出します。これは v0.7.5 で開ける通常のスキーマ 4 のデータベースです。コピーを書き出せない場合は何も変わらず、バックエンドは起動しません。
2. **スキーマ v5 への移行**（1 つのトランザクションで実行）：`users` に 2 つの新しい列、`ai_enabled`（**AI+**。全員オフ）と `uid`（ユーザーごとのランダムな識別用のスタンプ）が加わります。ほかは何も変わりません：問題集、記録、設定、アカウント、セッションは残り、誰もログアウトされません。ログには `Upgraded the database to schema 5. A copy of the previous version was saved first: /data/backups/xexam-schema4-….db (…)` と出ます。
3. **内部トークン。** バックエンドはランダムなトークンを（`xexam_link` の）`/link/internal.token` に書き込み、`AI link: /link/internal.token` とログに出します。`XEXAM_INTERNAL_TOKEN` を設定しているときはファイルを書かず、`AI link: using XEXAM_INTERNAL_TOKEN` とログに出します。

ai-service は初めての起動で、既定の設定のデータベース `xexam-ai.db`（スキーマ 2）を作り、`XEXAM_AI_SECRET_KEY` を設定していなければキーファイル `secret.key` も作ります（`Created a new AI key file /data/secret.key`）。その後すぐに、そして 25 秒ごとにバックエンドへ報告するので、メインサービスは接続されていることを知ります（60 秒より古い報告は接続されていないものとして扱われます）。バックエンドから ai-service を呼び出すことはありません。管理者が **AI 設定**（[usage.md](usage.md) の第 17 節）で設定するまで、**AI はオフ** です。AI について移行するものはありません。（v0.8 のリリース前のビルドが書いた AI のデータベース、スキーマ 1 は、ai-service の最初の起動で、AI ボリューム内のそのすぐ隣にコピー `backups/xexam-ai-schema1-<YYYYMMDD-HHMMSS>.db` を書き出した後でアップグレードされます。このコピーを書き出せない場合、ai-service は起動せず、何も変更しません。それ以降のリリース前のビルドのスキーマ 2 のデータベースで、スキーマ 2 の列（`users.function_enabled`、`users.free_mode`、`messages.free`、`usage.tokens_cached`）の一部がないものは、起動のたびにそれらが追加され、コピーは作りません：この段階は足りない列を追加するだけで、列を削除することはないので、そのようなビルドの古い `chats.free` 列は、使われないまま残ります。）

ほかに気づく点：

- メニューに **AI チャット** と **AI 設定**（AI チャットは、AI がオンになってから、管理者と **AI+ 機能** を持つユーザーに）。**AI 設定** は常に開き、ai-service が接続されているかを表示します。AI がオンになると、管理者は **設定** に **AI 対話モード**（**通常モード** / **フリーモード**）を見つけられます。
- **ユーザー管理**：ユーザーごとに **AI+ 機能** のスイッチ（ai-service が接続されていて、AI 設定で **AI+ 機能** がオンの間だけ表示されます。ユーザーの **一時停止** と **再開** は AI 設定の **AI+ ユーザー** にあります）。**変更** と **ユーザーを追加** の問題集の選択がコンパクトになり（一覧の上の 1 行に **問題集を管理**、**すべて選択**、**すべて解除**、一覧の最初の項目に **今後インポートする問題集も含める**、説明はツールチップ）、**問題集を管理** は **編集** からそこに移りました。
- ヘッダー、ブラウザのタブ、スマートフォンのホーム画面の新しいアイコン（以前に追加したホーム画面のアイコンは、追加し直すまで古い絵のままのことがあります）。

（v0.7.5 ではなく）v0.7 から更新する場合は、v0.7.5 の変更も一緒に入ります（README の更新履歴を参照）。データベースの手順は同じです。

**v0.7 のリリース前のビルド** が書いたデータベース（まだ列 `users.all_banks` があるもの）は、同じ起動のときに、同じトランザクションで、同じ 1 つのコピー（`xexam-schema4-…`）の後に変換されます：すべての問題集を見られたユーザーは、既存のすべての問題集と **今後インポートする問題集も含める** を受け取り、ほかのユーザーは自分の問題集をそのまま持ち、その間に古いバージョン（v0.6 以前）が追加したユーザーも、すべての問題集と **今後インポートする問題集も含める** を受け取ります。このときログには `Converted the question bank access of a database written by a v0.7 pre-release to the released format and upgraded the database to schema 5. A copy of the previous version was saved first: <path>.` と出ます（[database.md](database.md) の 6.5 節）。

### 1.2 アップグレード

```bash
# 1. ボリュームをバックアップ（先に停止。バックアップファイルにはデータベース全体が入るので、コミットしない）
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data-v075.tgz -C /data .

# 2. docker-compose.yml を新しいファイルに差し替える（.env はそのまま。docker-compose.yml を自分で変更していた場合は、その変更を引き継ぐ）
curl -fLO https://raw.githubusercontent.com/Yumin-Space/xexam/main/docker/docker-compose.yml

# 3. 3 つのイメージを pull して起動（down -v は使わない）
docker compose pull
docker compose up -d

# 4. アップグレードのメッセージと AI サービスの起動を確認
docker compose ps
docker compose logs backend
docker compose logs ai-service
```

- **任意、手順 3 の前に**：AI の暗号化キーを AI のボリュームから切り離しておくには、今のうちに `docker/.env` に `XEXAM_AI_SECRET_KEY=<openssl rand -base64 32 の出力>` を書いてください。後から設定してもかまいませんが、その場合、それまでに保存した AI のキーは復号できなくなり、入力し直す必要があります。`XEXAM_INTERNAL_TOKEN` も任意です。設定しなければバックエンドがトークンを作ります（[deployment.md](deployment.md) の第 3 節）。
- **`/etc/localtime` のないホスト**：新しい compose ファイルは、これを AI サービスにもマウントします。両方のサービスでその 6 行を削除し、`docker/.env` で `TZ` を設定してください。
- **AI サービスがインターネットに出られない**（厳しいファイアウォールの後ろのホスト）：Xexam は動きます。AI サービスがプロバイダーに届くようになるまで（または自分のネットワークのプロバイダーを指定するまで）、AI 設定のテストが「AI プロバイダーに接続できませんでした」で失敗するだけです。
- **ソースからビルドしている場合**：リポジトリのルートで `git pull && docker compose -f docker/docker-compose.build.yml up -d --build`。`ai-service/Dockerfile` を 3 つ目のイメージ `xexam-ai-service:local` としてビルドします。
- **v0.8 のリリース前のビルドから更新する場合**（AI サービスがまだ `ai` という名前の compose ファイル）：新しいファイルで `docker compose up -d --remove-orphans` を実行すると、古いコンテナが削除されます。ボリューム `xexam_ai_data` と `xexam_link` は再利用されます。その名前のリリース版はなかったので、v0.7.5 からの通常のアップグレードでは削除するものはありません。

### 1.3 アップグレード後の確認

- [ ] `docker compose ps` に `xexam-frontend`、`xexam-backend`、`ai-service` が並び、すべて `healthy`。
- [ ] `/api/info` の `version` が `0.8`。
- [ ] これまでどおりログインできる。誰もログインし直す必要がなかった。**ユーザー管理** には同じユーザーが並び、一般ユーザーはどれも **AI+ 機能** がオフ（スイッチは、ai-service が接続されて、AI 設定で **AI+ 機能** がオンになると表示されます）。
- [ ] **システムログ** に `AI: AI link: connected to the main service` が 1 回ある（AI サービスの行は `AI: ` で始まる。この行は再接続のたびにまた出て、接続が切れたときは `AI: AI link: lost the main service` が出ます）。
- [ ] **AI 設定** が開き、**ai-service は接続されています（バージョン 0.8、…）** と **AI+ 機能はオフ** が表示され、接続を保存するまで最初のチップは **接続が未設定** と表示される。AI を試すには：プロバイダーを設定し、**テスト** して **AI+ 機能** をオンにし、**AI チャット** で何か質問する。代わりに **ai-service の接続状態** と表示されたときは、そこに書かれた原因を読む（[usage.md](usage.md) の第 17 節）。
- [ ] これからは 2 つのデータボリュームの両方をバックアップする（[database.md](database.md) の第 5 節と 8.4 節）。

### 1.4 v0.7.5 へのロールバック

ロールバックとは、**移行前に書き出されたコピーを元に戻し**、古い `docker-compose.yml` を元に戻して、v0.7.5 のイメージを実行することです。移行の後にメインのアプリで行ったことはすべて失われます（記録、アカウント、設定、インポート）。AI のデータは、v0.7.5 が使わない専用のボリュームに残ります。

```bash
# 1. 新しいバージョンを停止（down -v は使わない）
docker compose stop

# 2. コピーを探す。正常に停止していれば、/data に xexam.db-wal が残っていても空
docker run --rm -v xexam_data:/data alpine ls -l /data /data/backups

# 3. コピーを xexam.db として戻す（ファイル名は手順 2 で確認したものを使う）。残っている -wal / -shm のファイルは先に削除する
docker run --rm -v xexam_data:/data alpine sh -c 'rm -f /data/xexam.db-wal /data/xexam.db-shm && cp /data/backups/xexam-schema4-20261111-140501.db /data/xexam.db'

# 4. v0.7.5 の docker-compose.yml を、2 つのイメージを固定して元に戻してから（Docker Hub にあり、ログイン不要）起動：
#      image: docker.io/yuminspace/xexam-backend:v0.7.5
#      image: docker.io/yuminspace/xexam-frontend:v0.7.5
#    そして、古いファイルがもう知らない停止した `ai-service` コンテナを削除する（そのボリュームは残る）：
docker compose up -d --remove-orphans
```

ソースからビルドしている場合は、代わりにリリースをチェックアウトします：`git fetch --tags && git checkout v0.7.5 && docker compose -f docker/docker-compose.build.yml up -d --build --remove-orphans`。

v0.7.5 は移行済みのデータベースそのものも開けます（2 つの新しい列を無視します）が、これは緊急のときだけにしてください：v0.7.5 が作ったユーザーには識別用のスタンプがなく、AI+ はオフで、v0.8 は次の起動のときにそのユーザーにスタンプを設定します（[database.md](database.md) の 6.6 節）。ボリューム `xexam_ai_data` と `xexam_link` は、後のアップグレードのために残しておけます。`docker volume rm xexam_ai_data xexam_link` で削除できます（AI のチャット、メモ、設定は完全に消えます）。

あとで再びアップグレードするときは、新しい `docker-compose.yml` を元に戻して `docker compose pull && docker compose up -d` を実行します。移行がもう一度行われ、新しいコピーが書き出されます。`xexam_ai_data` の AI 設定とチャットはそのまま残っていて、もう存在しないユーザーの AI データは AI サービスが削除します。

### 1.5 テスト済みの内容

合成データだけを使っています（`backend/tests/v08_ai_link.rs`、`db_golden.rs`、`ai-service/tests/`、`tests/integration/`）：

- v0.7.5 が書いたスキーマ 4 のデータベースは、ちょうど 1 つの `xexam-schema4-…` のバックアップを取ってスキーマ v5 に移行される。すべてのユーザーが AI+ オフと、重複のない 16 進 32 桁のスタンプを受け取る。結果の `sqlite_master` は新しいデータベースと同じで、もう一度開いても何も書き込まない。
- スキーマ 3 のデータベースは、1 つの `xexam-schema3-…` のバックアップを取って一度にスキーマ v5 に移行される。リリース前の v4 のデータベースは、1 つのトランザクションで変換されて移行される。
- ロールバックの後に v0.7.5 が作ったユーザーは、次の起動のときに、バックアップなしでスタンプを受け取る。
- バックエンドは最初の `serve` で `internal.token`（モード 0600）を作り、再起動ではそれを使い続け、`XEXAM_INTERNAL_TOKEN` があれば作らず、規則に合わない値では接続をオフにしてログを 1 行出す。
- 3 つのイメージと架空のプロバイダーを使ったスタック全体（`stack_check.py`）：ログイン、AI 設定、テスト、有効化、keep-alive のコメント付きのストリーミングの回答、回答中の **AI+ 機能** のオフ（数秒以内に終わる）と回答中のユーザーの一時停止（すぐに終わる）、ai-service が接続されていない間や機能がオフの間に拒否されるユーザー管理の AI+ のスイッチ、ai-service の `docker stop` と `docker start` の後の接続状態、返答言語、管理者のフリーモード（設定で選び、ユーザーごとに保持され、送信に `free` が含まれていても無視され、以前のチャットごとのルートは 404 を返す）、コンテナを作り直しても残る AI 設定とデータ、`ai-service` の停止中も応答するメインのアプリ、各ボリュームが持つファイル、そしてどのログや応答にもキー、質問、回答が含まれないこと。停止、再試行、上限、バックエンドへの報告、AI のデータベースのスキーマ 2 へのアップグレード、管理者のアクセスは `ai-service/tests/` でテストしている。

テストしていないもの：**ご自身の** データベースの移行と、本物の AI プロバイダー（CI は架空のものを使います）。確実にしたい場合は、まずコピーでアップグレードを試してください。

## 2. v0.6 から v0.8 へのアップグレード

### 2.1 何が変わるか

お使いのデータボリュームで新しいバージョンを**初めて起動**すると、リクエストを受け付ける前に次の処理を行います：

1. **バックアップ。** 現在のデータベースのコピーを `/data/backups/xexam-schema3-<YYYYmmdd-HHMMSS>.db` に書き出します。このコピーは通常のスキーマ 3 のデータベースで、v0.6 で開けます。**コピーを書き出せない場合**（ディスクがいっぱい、権限がないなど）、バックエンドは起動を中止し、データベースには手を付けません。理由はログに出ます。
2. **スキーマ v5 への移行**（v4 を経由、1 つのトランザクションで実行）：
   - **既存のユーザーは、引き続きすべての問題集を使えます**：それぞれが既存のすべての問題集と **今後インポートする問題集も含める** を受け取り、ユーザー管理では **問題集：すべて（今後インポートするものも含む）** と表示されます。これから追加するユーザーは、選ぶまで問題集なしで始まります。
   - **既存の問題集は、すべて最初の管理者のものになります**（id がいちばん小さい有効な管理者）。**問題集を管理できる** 権限を持つユーザーは、まだいません。
   - **既存の学習記録は、すべて試験になります。** 練習の記録が現れるのは、これからです。
   - **AI+** は全員オフで、すべてのユーザーが識別用のスタンプを受け取ります（v5 の段階。1.1 節）。
   - 問題 id、統計、記録、設定、アカウント、セッションは変わりません。誰もログアウトされません。
3. **WAL モード。** 移行に成功した後でだけ、バックエンドはデータベースを WAL に切り替えます。動作中は `xexam.db` の隣に `xexam.db-wal` と `xexam.db-shm` があり、正常に停止すると、それらは `xexam.db` に書き戻され、`xexam.db-wal` は空になります（2 つのファイルは空のまま残ることがありますが、害はありません）。
4. **古い形式の問題を出題停止にします**。これはもう 1 つのトランザクションで行います：3 列・4 列形式から取り込んだ有効な問題（v0.6 ではすべての問題）は、インポートがワークブックからなくなった問題を出題停止にするのとまったく同じように、出題停止になります。問題集、その取り込み履歴、学習記録、統計、間違いノートは残ります。問題はもう出題されず、問題集の一覧には、その問題集の問題が古い Excel 形式のものだったことが表示されます。ログには問題集ごとに警告が 1 行出ます。たとえば `retired 12 questions of bank "Kitchen basics": they use the old 3- / 4-column layout; import the six-column version of the workbook` です。この確認は起動のたびに（コマンドラインのコマンドでも）行い、出題停止にするものがなければ何も書き込みません。

ほかに気づく点：

- **インポートできるのは 6 列形式のワークブックだけです。** 3 列や 4 列のファイルは、そう伝えるメッセージとともに拒否されます（[usage.md](usage.md) の第 12 節）。
- **ユーザー管理** では、各行にそのユーザーの問題集が表示され、**変更** で選べます（問題集の管理権限である **問題集を管理** もここ）。**AI+** のスイッチもあります。問題集を外しても、その問題集のユーザーの記録は履歴として残ります。
- ホームの **試験を開始** の隣に **練習を開始** があります。練習の記録は、**学習記録** で **練習** のタグが付きます。
- 管理者のメニューに **システムログ** と **AI 設定** があり、AI を設定すると **AI チャット** も表示されます（1.1 節）。
- 答えと解説の各カードに **English** / **中文** / **日本語** の切り替えがあります。

新しい `docker-compose.yml` は、v0.6 のものと次の点で違います：2 つのボリュームとネットワーク `egress` を伴う AI サービスがある（1.1 節）、決まった既定のタイムゾーンではなくホストのタイムゾーンに従う（`/etc/localtime` をマウントします。`docker/.env` の `TZ` はそれより優先されます）、各コンテナのログを 10 MB のファイル 3 つまでに制限する、`docker/.env` で設定したときに `XEXAM_SQLITE_JOURNAL`、`XEXAM_COOKIE_SECURE`、`XEXAM_LOG`、AI の変数を渡す。v0.6 のファイルでも新しいバージョンは起動しますが、これらの変更はなく、AI もありません。`.env` に追加しなければならない変数はありません。

### 2.2 アップグレードの前に

- [ ] 使っている各ワークブックの **6 列形式の版** を用意する：A〜C 列に英語・中国語・日本語の問題、D〜F 列に同じ 3 言語の答えと解説を書き、英語を基準にします（[usage.md](usage.md) の第 12 節）。中国語や日本語がない箇所は空のままでかまいません。
- [ ] 各問題集の問題数を控える（**問題集の管理** のページ）。アップグレードの後で比べられるようにします。
- [ ] 未提出の試験は提出するか破棄する：その問題はアップグレードで出題停止になるので、その後は続きから回答できません。

### 2.3 アップグレード

```bash
# 1. ボリュームをバックアップ（先に停止する。バックアップファイルにはデータベース全体が入っているので、コミットしない）
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data-v06.tgz -C /data .

# 2. docker-compose.yml を新しいファイルに差し替える（.env はそのまま。docker-compose.yml を自分で変更していた場合は、その変更を移す）
curl -fLO https://raw.githubusercontent.com/Yumin-Space/xexam/main/docker/docker-compose.yml

# 3. 新しいバージョンを pull して起動（down -v は使わない）
docker compose pull
docker compose up -d

# 4. アップグレードのメッセージ、コピーのファイル名、ジャーナルモード、出題停止になった問題を確認
docker compose logs backend
```

ログには `Upgraded the database to schema 5. A copy of the previous version was saved first: /data/backups/xexam-schema3-20261111-140501.db (…)`、`SQLite journal mode: wal`、問題集ごとに 1 行の `retired … of bank "…"` の警告が出るはずです。

- **タイムゾーン。** v0.6 の compose ファイルは、`.env` で別のものを指定しない限り、決まったタイムゾーンを設定していました。ホストのタイムゾーンが、これまでのタイムスタンプが書かれたタイムゾーンと違う場合は、新しい記録も同じタイムゾーンで続くように、そのタイムゾーンを `docker/.env` の `TZ` に設定してください（例：`TZ=UTC`）。保存済みの日時が書き換えられることはありません。
- **`/etc/localtime` のないホスト**：Compose は "bind source path does not exist" で止まります。`docker-compose.yml` からそのマウントの 6 行を（バックエンドと AI サービスの両方で）削除し、`docker/.env` で `TZ` を設定してください（[deployment.md](deployment.md) の 3.1 節）。
- **特殊なストレージ**：ボリュームがネットワークファイルシステムや、Docker Desktop にバインドマウントした Windows のフォルダにある場合は、手順 3 の前に `docker/.env` に `XEXAM_SQLITE_JOURNAL=delete` を書いてください。
- **ソースからビルドしている場合**：リポジトリのルートで `git pull && docker compose -f docker/docker-compose.build.yml up -d --build`、続いて `docker compose -f docker/docker-compose.build.yml logs backend`。Docker を使わない場合、コピーはデータディレクトリ（`--data` または `XEXAM_DATA`）の中の `backups/` に書き出されます。

### 2.4 問題集を元に戻す

問題集ごとに：**問題集の管理** → **Excel の取り込み** → **既存を更新** で、**更新する問題集** でその問題集を選び、その 6 列形式のファイルを選んで確定します。

- 問題集の名前、所有者、それを見られるユーザーはそのままです。
- 6 列形式は英語の文で、古い形式は日本語の文で問題を識別するので、ファイルの問題はすべて新しい問題として回答履歴なしで **追加** され、古い問題は出題停止のままです。以前の学習記録には古い問題が **出題停止** のタグ付きで表示され、間違いノートは新しい問題で最初から始まります。
- 代わりに、6 列形式のファイルを **新しい問題集** としてインポートし、古い問題集を後で（学習記録ごと、または学習記録を残して）削除することもできます。

これより前にホームを開いたユーザーには、問題集に有効な問題がないという案内が表示されます。

### 2.5 アップグレード後の確認

- [ ] `/api/info` の `version` が `0.8` で、`docker compose ps` に healthy なコンテナが 3 つ並ぶ。
- [ ] これまでどおりログインできる。誰もログインし直す必要がなかった。
- [ ] **ユーザー管理**：以前からいるユーザーには、どれも **問題集：すべて（今後インポートするものも含む）** と表示されている。
- [ ] **問題集の管理** に同じ問題集が並び、どれも最初の管理者がアップロードしたものになっている。2.4 節の更新の前は、どれも問題が出題停止として表示され（たとえば **0 問（ほかに出題停止 25 問）**。控えた数）、更新の後は 6 列形式のファイルの問題数になる。
- [ ] **学習記録** に以前の記録が並び、どれにも **試験** のタグが付いている。
- [ ] **システムログ** に起動時の行があり、その中に `SQLite journal mode: wal` と出題停止になった問題がある。
- [ ] 短い練習を 1 回行い、**学習記録** のその日時を時計と比べる。ちょうど何時間かずれていたら、`TZ` を設定する（2.3 節）。
- [ ] そのうえで、ユーザーごとに見せる問題集と、誰に問題集を管理させるかを決める。AI は設定するまでオフ（1.1 節）。

### 2.6 v0.6 へのロールバック

ロールバックとは、**移行前に書き出されたコピーを元に戻し**、v0.6 のイメージを実行することです。移行後に行ったことはすべて失われます：6 列形式のインポート、新しい問題集、記録（練習の記録も）、アカウント、問題集の権限、設定。AI のデータは、v0.6 が使わない専用のボリュームに残ります。

```bash
# 1. 新しいバージョンを停止（down -v は使わない）
docker compose stop

# 2. コピーを探す。正常に停止していれば、/data に xexam.db-wal が残っていても空
docker run --rm -v xexam_data:/data alpine ls -l /data /data/backups

# 3. コピーを xexam.db として戻す（ファイル名は手順 2 で確認したものを使う）。残っている -wal / -shm のファイルは
#    置き換えるデータベースのもので、コピーに適用してはいけないので、先に削除する
docker run --rm -v xexam_data:/data alpine sh -c 'rm -f /data/xexam.db-wal /data/xexam.db-shm && cp /data/backups/xexam-schema3-20261111-140501.db /data/xexam.db'

# 4. docker-compose.yml で v0.6 のイメージを指定し（Docker Hub にあり、ログイン不要）、ファイルから ai のサービス（とそのボリューム）を
#    削除するか、v0.6 の docker-compose.yml を元に戻してから起動：
#      image: docker.io/yuminspace/xexam-backend:v0.6
#      image: docker.io/yuminspace/xexam-frontend:v0.6
docker compose up -d --remove-orphans
```

ソースからビルドしている場合は、代わりにリリースをチェックアウトします：`git fetch --tags && git checkout v0.6 && docker compose -f docker/docker-compose.build.yml up -d --build --remove-orphans`。

手順 3 の代わりに、2.3 節で作った自分用の `.tgz` を復元してもかまいません（復元コマンドは [database.md](database.md) の第 5 節にあります）。中身は同じデータです。手順 4 はどちらの場合も必要です。

v0.6 は移行済みのデータベースそのものも開け、ファイルを WAL から自分で元に戻しますが、これは緊急のときだけにしてください。v0.6 は v0.7 以降の規則を知らないので、全員が再びすべての問題集を見られるようになり、問題集を管理できるのは管理者だけになり、練習の記録は試験のように見え、6 列形式の問題についても何も知りません。その後で新しいバージョンがもう一度起動すると、v0.6 が残したものを直します（[database.md](database.md) の 6.6 節）：v0.6 が取り込んだ問題集には所有者が付き、**今後インポートする問題集も含める** のユーザーに届きます。v0.6 が作ったユーザーには、すべての問題集と **今後インポートする問題集も含める** が設定され、v0.6 が取り込んだ問題はもう一度出題停止になります。

あとで再びアップグレードするときは、新しいイメージ（タグ `:latest`）に戻して `docker compose pull && docker compose up -d` を実行します。移行がもう一度行われ、新しいコピーが書き出されます。

### 2.7 テスト済みの内容

合成データだけを使っています（`backend/tests/v065_bank_access_and_practice.rs`、`v07_bank_access_and_layouts.rs`、`v07_wal_and_logs.rs`、`v08_ai_link.rs`、`db_golden.rs`、`tests/integration/`）：

- スキーマ 3 のデータベースは、1 つのバックアップを取ったうえでスキーマ v5 に移行される。どのユーザーも、今後インポートする問題集も含めてすべての問題集を使え続け、問題集は最初の管理者のものになる。
- バックアップを書き出せない場合、データベースは移行されず、変更もされない。
- 古い形式の問題は、問題集、記録、間違いノートを残したまま一度だけ出題停止になる。2 回目の起動では何も書き込まない。コマンドラインのプログラムも同じことをし、問題集ごとに英語の行を 1 行記録する。問題が出題停止になった問題集を 6 列形式のファイルで更新すると、新しい問題が追加され、古い問題は出題停止のままになる。
- アップロード、インポートの確定、コマンドラインの `import` は、何かを一時保存したり書き込んだりする前に、3 列と 4 列のワークブックを拒否する。
- v0.7 のリリース前のデータベースは、バックアップの後に変換される。その間に古いバージョンが追加したユーザーがいても同じ。
- 新しいデータベースは WAL モードになる。`XEXAM_SQLITE_JOURNAL=delete` では DELETE のままになり、それなしで次に起動すると、すべての記録を残したまま再び WAL になる。
- WAL モードのデータベースを移行すると、まだ `-wal` ファイルにあった変更もバックアップされる。バックアップはそれだけで完結した 1 つのファイルになる。
- 最新のデータベースを開いても、何も書き込まない（データベースファイルとその `-wal` ファイルは、どちらも 1 バイトも変わらない）。
- `docker stop` の後、ボリュームには `xexam.db` があり、`-wal` の中身はない。
- サーバーがデータベースを開いている間も、`reset-password` が使える。
- 所有者のいない問題集、ロールバックの後に古いバージョンが作った問題集とユーザー、古くなった問題集の割り当ては、次の起動時に直される。

テストしていないもの：**ご自身の**データベースの移行。確実を期したい場合は、まずコピーで試してください（第 6 節の「コピーで新バージョンを試す」と同じやり方です）。

## 3. v0.5 または v0.5.1 から v0.8 へのアップグレード

### 3.1 何が変わるか

v0.6 でアカウントとログインが加わり（スキーマ v3）、v0.7 でユーザーごとの問題集が（スキーマ v4）、v0.8 で AI+ のスイッチと識別用のスタンプが加わりました（スキーマ v5）。v0.5 から更新する場合は、**初めての起動**のときに、コピーを 1 つ書き出したうえで、そのすべてを 1 つのトランザクションで行います：

1. **バックアップ**：`/data/backups/xexam-schema2-<YYYYmmdd-HHMMSS>.db` に。v0.5 で開ける通常のスキーマ 2 のデータベースです。書き出せない場合は何も変わらず、バックエンドは起動しません。
2. **アカウント。** 既定の管理者 `admin`（パスワード `admin`）が作られ、**それまでのものをすべて受け取ります**：すべての学習記録、間違いノート、設定です。
3. **スキーマ v4 と v5**：2.1 節と同じです。`admin` がすべての問題集を見られ、所有します。AI はオフです（1.1 節）。
4. **WAL モード**、続いて **古い形式の問題の出題停止**：2.1 節と同じです。先に 6 列形式のワークブックを用意し（2.2 節）、その後でそれを使って問題集を更新してください（2.4 節）。

これからは、どのページにもログインしたアカウントが必要です。学習記録、間違いノート、設定は人ごとに分かれるので、`admin` を共有するのではなく、**ユーザー管理** でほかの人を追加してください。

### 3.2 アップグレード

2.3 節のコマンドを使います。バックアップの名前は `xexam-data-v05.tgz` にします。v0.5 の `docker-compose.yml` は、まだ `ghcr.io` から pull します。新しいファイルは Docker Hub（`docker.io/yuminspace/…`、公開、ログイン不要）から pull します。プロジェクト名とボリューム `xexam_data` は同じなので、データはそのまま残ります。

ログにはコピーの名前（`…/backups/xexam-schema2-….db`）と、`Created the default administrator 'admin' (password 'admin'); sign in and choose a new password.`（「既定の管理者 'admin'（パスワード 'admin'）を作成しました。ログインして新しいパスワードを設定してください。」）が出て、問題集ごとに出題停止になった問題が並びます。

### 3.3 アップグレード後の確認

- [ ] Xexam を開く：ログインページが表示され、アカウント `admin` の名前が出ている。`admin` / `admin` でログインし、すぐに自分のパスワードを設定する。それまでは、このページを開ける人なら誰でも既定のパスワードを使える。
- [ ] `/api/info` の `version` が `0.8`。
- [ ] **問題集の管理** に同じ問題集が並び、更新するまで（2.4 節）その問題は出題停止になっている。**学習記録** に以前の試験が並んでいる。**設定** にあなたのテーマと言語がある。
- [ ] ほかのユーザーを追加し、それぞれの問題集を選ぶ。

### 3.4 v0.5 へのロールバック

2.6 節と同じですが、コピーは `xexam-schema2-….db`、イメージは `docker.io/yuminspace/xexam-backend:v0.5.1` と `docker.io/yuminspace/xexam-frontend:v0.5.1` を使います（v0.5 そのものは、非公開のミラー `ghcr.io/yumin-space/` にしかありません）。アップグレード以降に行ったことは、アカウントも含めてすべて失われます。

移行済みのデータベースで v0.5 を動かさないでください。v0.5 はアカウントを知らないので、その記録は誰のものでもなくなり（新しいバージョンは次の起動時に、それを最初の管理者のものにします）、全員が再び 1 つの間違いノートを共有することになります。

## 4. v0.4 から v0.5 以降へのアップグレード

現在、このアップグレードは v0.8 まで一気に進みます：下の手順に続いて 3.1 節と 2.1 節の手順が、**1 つ** のコピー `xexam-schema1-<YYYYmmdd-HHMMSS>.db` を書き出したうえで、**1 つ** のトランザクションで行われ、その後で古い形式の問題が出題停止になります（2.1 節の手順 4）。その後は `admin` / `admin` でログインし（3.3 節）、`admin` がすべてのデータを受け取ります。先に 6 列形式のワークブックを用意してください（2.2 節）。

### 4.1 データはどうなるか

v0.5 では、データベースに問題集、試験ごとの各問題の詳細、設定が加わりました（スキーマ v2）。変更は追加だけです。作り直されるものはなく、問題 id も 1 つも変わりません。詳しくは [database.md](database.md) の第 6 節を参照してください。

お使いのデータボリュームで新しいバージョンを**初めて起動**すると、バックエンドはリクエストを受け付ける前に次の処理を行います：

1. **バックアップ。** 現在のデータベースのコピーを、`xexam.db` と同じ場所の `backups/xexam-schema1-<YYYYmmdd-HHMMSS>.db` に書き出します（Docker では、ボリューム `xexam_data` 内の `/data/backups/`）。このコピーは通常のスキーマ 1 のデータベースで、v0.4 で開けます。既存のファイルを上書きすることはありません。**コピーを書き出せない場合**（ディスクがいっぱい、権限がないなど）、バックエンドは起動を中止し、データベースには手を付けません。理由はログに出ます。
2. **移行**（1 つのトランザクションで実行）：
   - 既存のデータはすべて **1 つの問題集**（「レガシー」問題集）になります。名前は、最後にインポートしたファイルの名前から `.xlsx` を除いたものです（一度もインポートしていなければ `Question bank`）。
   - **問題 id は変わりません。** そのため、問題ごとの統計、間違いノート、試験の履歴は、引き続きそれぞれの問題に結び付いています（その問題はその後、出題停止になります。上記を参照）。
   - **試験記録は残り**、この問題集の記録になります。ただし、問題ごとの詳細はありません。v0.4 は回答内容を保存していなかったためです。詳細ページには得点が表示されますが、回答は表示されず、「受け直し」のボタンもありません。
   - インポート履歴も残り、この問題集のものになります。

2 回目以降の起動では、直すべきものがないかを読み取りだけで確認し、何も書き込みません。

ほかに気づく点：

- **画面は英語で始まります。** v0.4 は中国語でした。**Settings → Language**（日本語表示では **設定 → 言語**）か、ログインページで変更できます。この設定はデータベースに保存されるので、一度設定すれば、どのブラウザ・端末でも同じになります。
- テーマは、**設定** で選ぶまでシステムの設定（ライトまたはダーク）に従います。
- 問題の言語（試験ページの日本語・中国語・英語）は、これまでブラウザが記憶していました。新しいバージョンをブラウザで初めて開いたとき、サーバー側がまだ既定値（日本語）のままであれば、その選択がサーバーに移されます。
- ブラウザに保存されている未提出の試験は、その問題がほかの問題と一緒に出題停止になるため、アップグレードの後は続きから回答できません。アップグレードの前に提出してください。
- データベースに残す記録の数が、60 件から、ユーザーごとに最新の 500 件に増えました。

### 4.2 アップグレード

`.env`、ポート、ボリュームは何も変わりません（[deployment.md](deployment.md) の第 6 節を参照）。v0.5.1 から変わったのは、`docker-compose.yml` のイメージの取得元だけです。`ghcr.io` ではなく Docker Hub（`docker.io/yuminspace/…`、公開、ログイン不要）から pull します。お使いの `docker-compose.yml` を新しいファイルに差し替えるか、その 2 つの `image:` の行を `docker.io/yuminspace/xexam-backend:latest` と `docker.io/yuminspace/xexam-frontend:latest` に変更してください。プロジェクト名とボリューム `xexam_data` は変わらないので、データはそのまま残ります。

```bash
# 1. ボリュームをバックアップ（先に停止する。バックアップファイルにはデータベース全体が入っているので、コミットしない）
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data-v04.tgz -C /data .

# 2. 新しい docker-compose.yml（Docker Hub のイメージ）を配置したうえで、現在のバージョンを pull して起動（down -v は使わない）
docker compose pull
docker compose up -d

# 3. アップグレードのメッセージとコピーのファイル名を確認
docker compose logs backend
```

ログには `Upgraded the database to schema 5. A copy of the previous version was saved first: /data/backups/xexam-schema1-20261110-140501.db (…)` のような行が出て、その後に問題集の出題停止になった問題が出るはずです。このコピーはプログラム自身が書き出します。手順 1 の `.tgz` は、ボリュームの外に置く自分用の 2 つ目のコピーです。

ソースからビルドしている場合：リポジトリのルートで `git pull && docker compose -f docker/docker-compose.build.yml up -d --build`。compose ファイルは `docker/` に移りました。このコマンドの前に、リポジトリのルートにある `.env` を `docker/.env` に移動し（Compose はルートの `.env` を読まなくなりました）、その後のコマンド（`logs backend` など）にも `-f docker/docker-compose.build.yml` を付けてください。Docker を使わない場合、コピーはデータディレクトリ（`--data` または `XEXAM_DATA`）の中の `backups/` に書き出されます。

### 4.4 v0.4 へのロールバック

ロールバックとは、**移行前に書き出されたコピーを元に戻し**、v0.4 のイメージを実行することです。移行後に新しいバージョンで行ったことはすべて失われます：アカウント、新しい問題集、インポート、記録、設定。

```bash
# 1. 新しいバージョンを停止（down -v は使わない）
docker compose stop

# 2. コピーを探す。正常に停止していれば、/data に xexam.db-journal はなく、xexam.db-wal が残っていても空
docker run --rm -v xexam_data:/data alpine ls -l /data /data/backups

# 3. コピーを xexam.db として戻す（ファイル名は手順 2 で確認したものを使う。残っている -wal / -shm のファイルは先に削除する）
docker run --rm -v xexam_data:/data alpine sh -c 'rm -f /data/xexam.db-wal /data/xexam.db-shm && cp /data/backups/xexam-schema1-20261110-140501.db /data/xexam.db'

# 4. v0.4 は非公開の GHCR ミラーにしかない（Docker Hub は v0.5.1 から）。docker login ghcr.io を実行してから、docker-compose.yml の 2 つのイメージを次のように変更
#      image: ghcr.io/yumin-space/xexam-backend:v0.4
#      image: ghcr.io/yumin-space/xexam-frontend:v0.4
docker compose up -d
```

ソースからビルドしている場合は、代わりにタグをチェックアウトします：`git checkout v0.4 && docker compose -f docker-compose.build.yml up -d --build`（このタグでは compose ファイルはまだリポジトリのルートにあり、Compose は `.env` もルートから読みます。`docker/.env` がある場合は、先にリポジトリのルートへコピーしてください）。

手順 3 の代わりに、4.2 節で作った自分用の `.tgz` を復元してもかまいません（復元コマンドは [database.md](database.md) の第 5 節にあります）。中身は同じデータです。手順 4 はどちらの場合も必要です。

コピーを戻す代わりに、**移行済みのデータベースで v0.4 を実行しないでください**。v0.4 はこのファイルを開けますが、すべての問題集を 1 つとして扱います。次にインポートすると、ほかのすべての問題集の問題が出題停止になり、試験記録も 60 件に切り詰められ、アカウントのことも何も知りません。それでも実行してしまった場合は、次に新しいバージョンを起動したときに、v0.4 が追加した問題がレガシー問題集に組み込まれ（[database.md](database.md) の 6.6 節）、古い形式なので出題停止になります。

あとで再びアップグレードするときは、新しい `docker-compose.yml`（Docker Hub のイメージ、タグ `:latest`）に戻して `docker compose pull && docker compose up -d` を実行します。移行がもう一度行われ、新しいコピーが書き出されます。

### 4.5 テスト済みの内容

合成データだけを使っています（`backend/tests/v05_banks_records_settings.rs`、`v06_users_and_sign_in.rs`、`db_golden.rs`）：

- `sample.db`（旧 Python 実装が書き出したデータベース）は、すべての問題 id、統計、試験記録、インポート履歴を保ったまま現在のスキーマに移行される。そのバックアップは引き続きスキーマ 1 を示し、元の行をそのまま保持している。
- スキーマ 1 のデータベースは、スキーマ 1 のバックアップを 1 つ書き出したうえで、一度に現在のスキーマになる。
- バックアップを書き出せない場合、データベースは移行されず、変更もされない。
- 移行済みのデータベースをもう一度開いても、ファイルは 1 バイトも変わらない。
- 古いバイナリが移行済みのファイルに書き込んだ行は、次の起動時にレガシー問題集に組み込まれる。
- 新規作成したデータベースと移行したデータベースは、同じ構造になる。

テストしていないもの：**ご自身の**データベースの移行。確実を期したい場合は、まずコピーで試してください（第 6 節の「コピーで新バージョンを試す」と同じやり方です）。

## 5. Python から Rust へ（v0.3）：原則

1. **原本には触れません。** まずバックアップを取り、コピーで試し、問題がないことを確認してから切り替えます。
2. **いつでも戻せました。** v0.4 までは、2 つの実装が同じファイル、同じスキーマを読み書きします（移行時に合成データで双方向の往復を予行演習しました。第 9 節を参照）。v0.5 からはスキーマに新しいテーブルと列が加わったため、新しいバージョンから戻すには、移行前に書き出されたコピーを元に戻します（4.4 節）。
3. **旧実装は失われていません。** 旧コードは Git タグ `python-v0.2` にあり、旧イメージ `ghcr.io/yumin-space/xexam:v0.2.2`（および `:v0.2`、`:v0.2.1`）も引き続き GHCR にあって（非公開なので、pull するには `docker login ghcr.io` が必要です。Docker Hub にはありません）、新しいパイプラインで上書きされることはありません。リポジトリのメインブランチに Python コードはもうありません。

## 8. Python から Rust へ：ロールバック

Python 版に戻すことができます。旧バージョンの compose ファイルはもうメインブランチにないため、タグから取り出します：

```bash
# 1. 新バージョンを停止（down -v は実行しない）
docker compose stop

# 2. 旧バージョンの compose ファイルを取り出して、旧バージョンを起動（非公開の GHCR から ghcr.io/yumin-space/xexam:latest を pull するので、先に docker login ghcr.io を実行します。バージョンを固定したい場合は :latest を :v0.2.2 に書き換えてください）
git show python-v0.2:docker-compose.yml > docker-compose.legacy.yml
docker compose -f docker-compose.legacy.yml up -d
```

旧 compose のイメージタグは `:latest` ですが、**`ghcr.io/yumin-space/xexam:latest` は今回のリリース以降更新されません**（新しいイメージは `xexam-frontend` / `xexam-backend` という 2 つの新しい名前を使っています）。そのため、最後の Python 版を指したままになります。念のため、明示的に `:v0.2.2` と書いてください。

**v0.3 または v0.4 から戻す場合**、旧バージョンは引き続き同じ `xexam_data` ボリュームを使い、データは失われません。これらのバージョンが書き込んだデータ（新しくインポートした問題、新しい成績）は、すべて旧バージョンで読めます。これらのバージョンはスキーマを変更せず、`journal_mode` も変更せず、テーブルや列を追加せず、`user_version` も設定せず、`-wal` / `-shm` ファイルも残さないからです。

**v0.5 以降から戻す場合**、スキーマには新しいテーブルと列が加わっています（v0.7 からはファイルも WAL モードです）。まず 4.4 節の手順 1〜3 のとおり、移行前に書き出されたスキーマ 1 のコピーを元に戻し、それから上記の方法で旧バージョンを起動してください。

データまでアップグレード前の状態に戻したい場合（たとえば、新バージョンがデータを壊した疑いがあるとき）：

```bash
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine sh -c 'rm -f /data/xexam.db-wal /data/xexam.db-shm && tar xzf /backup/xexam-data.tgz -C /data'
docker compose -f docker-compose.legacy.yml up -d
```

> リストアは、バックアップで `/data` を上書きします。バックアップの後に新バージョンで行った変更はすべて失われます。本当に必要だと確認できたときだけ実行してください。

Docker を使わないロールバック：`git checkout python-v0.2` を実行し、`python server.py` を起動します（Python 3.8 以上が必要です）。データディレクトリは同じ `xexam.db` を指すようにします。

## 9. Python から Rust へ：予行演習で確認したこと

移行時（Python コードがまだ残っていたとき）に次の項目を行いました。**すべて架空のデータだけを使い**、実際のデータベースを読み取ったり、出力したり、変更したりしたことは一度もありません。旧 Python をその場で実行する必要があるスクリプトは、旧コードとともに削除しました。結論は、コミット済みのスナップショットテストが引き続き守っています。

| 予行演習 | 方法 | 結果 | 現在それを守っているもの |
|---|---|---|---|
| 新旧の双方向往復 | 旧 Python でデータベースを作成 → バックアップ + `integrity_check` → Rust が**コピー**を読む（旧バージョンとバイト単位で同一）→ Rust が 2 つ目のワークブックをインポートして成績を記録 → 旧 Python が読み戻す（Rust と同一）→ 旧 Python がさらに書き込む → Rust が再び読む | 19 項目に合格（「原本の sha256 が前後で変わらない」ことを含む） | `db_golden.rs`：`sample.db`（旧実装が書き出したデータベース）はすべての行を保ったまま現在のスキーマに移行され、移行後のファイルは、その後に開いて、読み取って、閉じても 1 バイトも変わらない。新規作成したデータベースの `sqlite_master` は、旧実装のテキストにその後の追加分を加えたもの |
| ゴールデンレスポンスとの突き合わせ | 172 件の旧バージョンのレスポンスを新バックエンドと項目ごとに比較 | 説明のつかない差異は 0 件、23 件は登録済み | `api_golden.rs` が CI のたびに再生する |
| セキュリティプローブ | 340 件の悪意あるリクエストを旧バージョンと新バージョンの両方に送信、設定は 3 種類 | 説明のつかない差異は 0 件、51 件は登録済み（多くは新バージョンのほうが厳格） | プローブのスクリプトは削除済み。ガードとアップロード検査は `api_*.rs`、`parser_hardening.rs`、`nginx_check.py` がテストしている |

## 10. Python から Rust へ：旧バージョンとの意図的な差異

理由付きの完全な表は [api.md](api.md) の第 7 節にあります。1 件ごとに `tests/baseline/golden/allowed_differences_rust.json` と `allowed_probe_differences_rust.json` に登録されており、登録のない差異があるとテストが失敗します。利用者から見えるものは次のとおりです：

| 項目 | 変更点 |
|---|---|
| アーキテクチャ | 1 つのコンテナが 2 つ（nginx + backend）になりました。イメージ名は `xexam-frontend` / `xexam-backend`。`XEXAM_BIND` は Nginx を指すようになりました |
| より厳格なアップロード検査 | どの文字コード / 拡張子であっても DOCTYPE を拒否。重複した ZIP エントリ名を拒否。エントリ数、XML の深さ、ノード数に上限あり |
| エラーメッセージ | 残りの中国語は一字一句そのまま保持。以前はライブラリの例外テキストをそのまま返していた 2 か所を、固定の中国語メッセージに変更 |
| 採点 | 引き続きブラウザ内で行い、サーバー側には移していません（仕様では移すことを勧めていますが、ここでは意図的に移していません。理由は [migration-plan.md](../zh-CN/history/migration-plan.md) の Q3 を参照） |
| iPhone | iOS 15.4 以上が必要（ビルドターゲット `safari15`） |
| 提供しなくなったもの | バックエンドによる静的ファイルの配信（Nginx が配信します）、`Server` レスポンスヘッダー |

その後のバージョンでの API の変更点は、[api.md](api.md) に一覧があります。

## 11. Python から Rust へ：検証していないもの

- 本物の Cloudflare Tunnel / Access、iPhone の実機、本物の ARM ハードウェア上での実行（arm64 は QEMU 上でビルドして起動を確認しただけです）。
- **ご自身の実データベース**のコピーを使った予行演習：こちらでは入手しておらず、読み取るべきでもありません。第 6 節に従って、ご自身のマシンで行ってください。

## 12. v0.1 からのアップグレード

データベースのファイル名は v0.2 から `xexam.db` です。データディレクトリに他の `.db` ファイルがあって `xexam.db` がない場合は、バックエンドの起動ログで警告されます。そのファイルを `xexam.db` に改名してから起動し直してください（古いファイルは削除されず、読み取られもしません）。古い `progress.json` は起動のたびに 1 回チェックされ、データベースにまだ学習記録がなく、かつ移行済みでない場合にだけ移行します。移行は 1 回限りで、既存の記録は上書きしません。
