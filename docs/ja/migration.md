# 移行とロールバック

> この文書では、すべてのアップグレード手順を新しい順に説明します：
>
> - **v0.6 → v0.7**（第 1 節）：データベースはスキーマ v4 と WAL モードに自動で移行します。移行の前に、バックアップのコピーが書き出されます。
> - **v0.5 または v0.5.1 → v0.7**（第 2 節）：ログインとスキーマ v4 が、一度に加わります。
> - **v0.4 → v0.5 以降**（第 3 節）：問題集、試験の詳細、設定（スキーマ v2）。現在は、その後のすべてと一緒に行われます。
> - **Python 版 v0.2.x → Rust + TypeScript + Nginx 版（v0.3）**（第 4〜10 節）：このときはデータベースファイルもスキーマも変わっていません。切り替えは「プログラムの入れ替え」であって「データの引っ越し」ではありませんでした。判断の根拠：[migration-plan.md](../zh-CN/history/migration-plan.md)。リスク：[risk-assessment.md](../zh-CN/history/risk-assessment.md)。
> - **v0.1 → それ以降**（第 11 節）：データベースのファイル名について。
>
> スキーマが変わるアップグレードでは、どれもまずデータベースのコピーを **1 つ** 書き出します。名前はそれまでのスキーマにちなんだもので、`xexam.db` と同じ場所の `backups/xexam-schema<N>-<YYYYmmdd-HHMMSS>.db` です（Docker では、ボリューム `xexam_data` 内の `/data/backups/`）。ロールバックとは、常に**そのコピーを元に戻し**、古いイメージを動かすことです。背景は [database.md](database.md) の第 6 節にあります。

## 1. v0.6 から v0.7 へのアップグレード

### 1.1 何が変わるか

お使いのデータボリュームで v0.7 を**初めて起動**すると、リクエストを受け付ける前に次の処理を行います：

1. **バックアップ。** 現在のデータベースのコピーを `/data/backups/xexam-schema3-<YYYYmmdd-HHMMSS>.db` に書き出します。このコピーは通常のスキーマ 3 のデータベースで、v0.6 で開けます。**コピーを書き出せない場合**（ディスクがいっぱい、権限がないなど）、バックエンドは起動を中止し、データベースには手を付けません。理由はログに出ます。
2. **スキーマ v4 への移行**（1 つのトランザクションで実行）：
   - **既存のユーザーは、引き続きすべての問題集を使えます**（`all_banks = 1`。**すべての問題集（今後インポートするものも含む）** と表示されます）。これから追加するユーザーは、選ぶまで問題集なしで始まります。
   - **既存の問題集は、すべて最初の管理者のものになります**（id がいちばん小さい有効な管理者）。**問題集を管理できる** 権限を持つユーザーは、まだいません。
   - **既存の学習記録は、すべて試験になります。** 練習の記録が現れるのは、これからです。
   - 問題 id、統計、記録、設定、アカウント、セッションは変わりません。誰もログアウトされません。
3. **WAL モード。** 移行に成功した後でだけ、バックエンドはデータベースを WAL に切り替えます。動作中は `xexam.db` の隣に `xexam.db-wal` と `xexam.db-shm` があり、正常に停止すると、それらは `xexam.db` に書き戻され、`xexam.db-wal` は空になります（2 つのファイルは空のまま残ることがありますが、害はありません）。

ほかに気づく点：

- **ユーザー管理** では、各行にそのユーザーの問題集が表示され、**変更** で絞り込めます。**ユーザーを追加** のフォームと **編集** のダイアログには **問題集を管理できる** の権限があります。問題集を外しても、その問題集のユーザーの記録は履歴として残ります。
- ホームの **試験を開始** の隣に **練習を開始** があります。練習の記録は、**学習記録** で **練習** のタグが付きます。
- 管理者のメニューに **システムログ** の項目があります。
- 答えと解説の各カードに **English** / **中文** / **日本語** の切り替えがあり、6 列形式のワークブックを取り込めます（**新しい問題集** として取り込んでください。README を参照）。

新しい `docker-compose.yml` は、v0.6 のものと 3 つの点で違います：決まった既定のタイムゾーンではなくホストのタイムゾーンに従う（`/etc/localtime` をマウントします。`docker/.env` の `TZ` はそれより優先されます）、各コンテナのログを 10 MB のファイル 3 つまでに制限する、`docker/.env` で設定したときに `XEXAM_SQLITE_JOURNAL` を渡す、の 3 つです。v0.6 のファイルでも v0.7 は起動しますが、これらの変更はありません。`.env` に追加しなければならない変数はありません。

### 1.2 アップグレード

```bash
# 1. ボリュームをバックアップ（先に停止する。バックアップファイルにはデータベース全体が入っているので、コミットしない）
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data-v06.tgz -C /data .

# 2. docker-compose.yml を新しいファイルに差し替える（.env はそのまま。docker-compose.yml を自分で変更していた場合は、その変更を移す）
curl -fLO https://raw.githubusercontent.com/Yumin-Space/xexam/main/docker/docker-compose.yml

# 3. v0.7 を pull して起動（down -v は使わない）
docker compose pull
docker compose up -d

# 4. アップグレードのメッセージ、コピーのファイル名、ジャーナルモードを確認
docker compose logs backend
```

ログには `Upgraded the database to schema 4. A copy of the previous version was saved first: /data/backups/xexam-schema3-20261111-140501.db (…)` と `SQLite journal mode: wal` が出るはずです。

- **タイムゾーン。** v0.6 の compose ファイルは、`.env` で別のものを指定しない限り、決まったタイムゾーンを設定していました。ホストのタイムゾーンが、これまでのタイムスタンプが書かれたタイムゾーンと違う場合は、新しい記録も同じタイムゾーンで続くように、そのタイムゾーンを `docker/.env` の `TZ` に設定してください（例：`TZ=UTC`）。保存済みの日時が書き換えられることはありません。
- **`/etc/localtime` のないホスト**：Compose は "bind source path does not exist" で止まります。`docker-compose.yml` からそのマウントの 6 行を削除し、`docker/.env` で `TZ` を設定してください（[deployment.md](deployment.md) の 3.1 節）。
- **特殊なストレージ**：ボリュームがネットワークファイルシステムや、Docker Desktop にバインドマウントした Windows のフォルダにある場合は、手順 3 の前に `docker/.env` に `XEXAM_SQLITE_JOURNAL=delete` を書いてください。
- **ソースからビルドしている場合**：リポジトリのルートで `git pull && docker compose -f docker/docker-compose.build.yml up -d --build`、続いて `docker compose -f docker/docker-compose.build.yml logs backend`。Docker を使わない場合、コピーはデータディレクトリ（`--data` または `XEXAM_DATA`）の中の `backups/` に書き出されます。

### 1.3 アップグレード後の確認

- [ ] `/api/info` の `version` が `0.7` で、`bankCount`（有効な問題の数）がアップグレード前と同じ。
- [ ] これまでどおりログインできる。誰もログインし直す必要がなかった。
- [ ] **ユーザー管理**：以前からいるユーザーには、どれも **問題集：すべて（今後インポートするものも含む）** と表示されている。
- [ ] **問題集の管理** に同じ問題集が並び、どれも最初の管理者がアップロードしたものになっている。
- [ ] **学習記録** に以前の記録が並び、どれにも **試験** のタグが付いている。間違えた問題の復習の問題数が以前と同じ。
- [ ] **システムログ** に起動時の行があり、その中に `SQLite journal mode: wal` がある。
- [ ] 短い練習を 1 回行い、**学習記録** のその日時を時計と比べる。ちょうど何時間かずれていたら、`TZ` を設定する（1.2 節）。
- [ ] そのうえで、ユーザーごとに見せる問題集と、誰に問題集を管理させるかを決める。

### 1.4 v0.6 へのロールバック

ロールバックとは、**移行前に書き出されたコピーを元に戻し**、v0.6 のイメージを実行することです。移行後に v0.7 で行ったことはすべて失われます：新しい問題集、インポート、記録（練習の記録も）、アカウント、問題集の権限、設定。

```bash
# 1. v0.7 を停止（down -v は使わない）
docker compose stop

# 2. コピーを探す。正常に停止していれば、/data に xexam.db-wal が残っていても空
docker run --rm -v xexam_data:/data alpine ls -l /data /data/backups

# 3. コピーを xexam.db として戻す（ファイル名は手順 2 で確認したものを使う）。残っている -wal / -shm のファイルは
#    置き換えるデータベースのもので、コピーに適用してはいけないので、先に削除する
docker run --rm -v xexam_data:/data alpine sh -c 'rm -f /data/xexam.db-wal /data/xexam.db-shm && cp /data/backups/xexam-schema3-20261111-140501.db /data/xexam.db'

# 4. docker-compose.yml で v0.6 のイメージを指定してから（Docker Hub にあり、ログイン不要）起動：
#      image: docker.io/yuminspace/xexam-backend:v0.6
#      image: docker.io/yuminspace/xexam-frontend:v0.6
docker compose up -d
```

新しい `docker-compose.yml` は、v0.6 のイメージでも使えます。ソースからビルドしている場合は、代わりにリリースをチェックアウトします：`git fetch --tags && git checkout v0.6 && docker compose -f docker/docker-compose.build.yml up -d --build`。

手順 3 の代わりに、1.2 節で作った自分用の `.tgz` を復元してもかまいません（復元コマンドは [database.md](database.md) の第 5 節にあります）。中身は同じデータです。手順 4 はどちらの場合も必要です。

v0.6 は移行済みのデータベースそのものも開け、ファイルを WAL から自分で元に戻しますが、これは緊急のときだけにしてください。v0.6 は v0.7 の規則を知らないので、全員が再びすべての問題集を見られるようになり、問題集を管理できるのは管理者だけになり、練習の記録は試験のように見えます。その後で v0.7 がもう一度起動すると、v0.6 が残したものを直します：v0.6 が取り込んだ問題集には所有者が付き、v0.6 が作ったユーザーには **すべての問題集** が設定されます（[database.md](database.md) の 6.6 節）。

あとで再びアップグレードするときは、v0.7 のイメージ（タグ `:latest`）に戻して `docker compose pull && docker compose up -d` を実行します。移行がもう一度行われ、新しいコピーが書き出されます。

### 1.5 テスト済みの内容

合成データだけを使っています（`backend/tests/v065_bank_access_and_practice.rs`、`v07_wal_and_logs.rs`、`db_golden.rs`、`tests/integration/`）：

- スキーマ 3 のデータベースは、バックアップを取ったうえでスキーマ v4 に移行される。どのユーザーもすべての問題集を使え続け、問題集は最初の管理者のものになる。
- バックアップを書き出せない場合、データベースは移行されず、変更もされない。
- 新しいデータベースは WAL モードになる。`XEXAM_SQLITE_JOURNAL=delete` では DELETE のままになり、それなしで次に起動すると、すべての記録を残したまま再び WAL になる。
- WAL モードのデータベースを移行すると、まだ `-wal` ファイルにあった変更もバックアップされる。バックアップはそれだけで完結した 1 つのファイルになる。
- 最新のデータベースを開いても、何も書き込まない（データベースファイルとその `-wal` ファイルは、どちらも 1 バイトも変わらない）。
- `docker stop` の後、ボリュームには `xexam.db` があり、`-wal` の中身はない。
- サーバーがデータベースを開いている間も、`reset-password` が使える。
- 所有者のいない問題集、古くなった問題集の割り当て、ロールバックの後に古いバージョンが作ったユーザーは、次の起動時に直される。

テストしていないもの：**ご自身の**データベースの移行。確実を期したい場合は、まずコピーで試してください（第 5 節の「コピーで新バージョンを試す」と同じやり方です）。

## 2. v0.5 または v0.5.1 から v0.7 へのアップグレード

### 2.1 何が変わるか

v0.6 でアカウントとログインが加わり（スキーマ v3）、v0.7 でユーザーごとの問題集が加わりました（スキーマ v4）。v0.5 から更新する場合は、**初めての起動**のときに、コピーを 1 つ書き出したうえで、両方を 1 つのトランザクションで行います：

1. **バックアップ**：`/data/backups/xexam-schema2-<YYYYmmdd-HHMMSS>.db` に。v0.5 で開ける通常のスキーマ 2 のデータベースです。書き出せない場合は何も変わらず、バックエンドは起動しません。
2. **アカウント。** 既定の管理者 `admin`（パスワード `admin`）が作られ、**それまでのものをすべて受け取ります**：すべての学習記録、間違いノート、設定です。
3. **スキーマ v4**：1.1 節と同じです。`admin` がすべての問題集を見られ、所有します。
4. **WAL モード**：1.1 節と同じです。

これからは、どのページにもログインしたアカウントが必要です。学習記録、間違いノート、設定は人ごとに分かれるので、`admin` を共有するのではなく、**ユーザー管理** でほかの人を追加してください。

### 2.2 アップグレード

1.2 節のコマンドを使います。バックアップの名前は `xexam-data-v05.tgz` にします。v0.5 の `docker-compose.yml` は、まだ `ghcr.io` から pull します。新しいファイルは Docker Hub（`docker.io/yuminspace/…`、公開、ログイン不要）から pull します。プロジェクト名とボリューム `xexam_data` は同じなので、データはそのまま残ります。

ログにはコピーの名前（`…/backups/xexam-schema2-….db`）と、`Created the default administrator 'admin' (password 'admin'); sign in and choose a new password.`（「既定の管理者 'admin'（パスワード 'admin'）を作成しました。ログインして新しいパスワードを設定してください。」）が出ます。

### 2.3 アップグレード後の確認

- [ ] Xexam を開く：ログインページが表示され、アカウント `admin` の名前が出ている。`admin` / `admin` でログインし、すぐに自分のパスワードを設定する。それまでは、このページを開ける人なら誰でも既定のパスワードを使える。
- [ ] `/api/info` の `version` が `0.7` で、`bankCount` がアップグレード前と同じ。
- [ ] **問題集の管理** に同じ問題集が並んでいる。**学習記録** に以前の試験が並び、間違えた問題の復習の問題数が以前と同じ。**設定** にあなたのテーマと言語がある。
- [ ] ほかのユーザーを追加し、それぞれの問題集を選ぶ。

### 2.4 v0.5 へのロールバック

1.4 節と同じですが、コピーは `xexam-schema2-….db`、イメージは `docker.io/yuminspace/xexam-backend:v0.5.1` と `docker.io/yuminspace/xexam-frontend:v0.5.1` を使います（v0.5 そのものは、非公開のミラー `ghcr.io/yumin-space/` にしかありません）。アップグレード以降に行ったことは、アカウントも含めてすべて失われます。

移行済みのデータベースで v0.5 を動かさないでください。v0.5 はアカウントを知らないので、その記録は誰のものでもなくなり（v0.7 は次の起動時に、それを最初の管理者のものにします）、全員が再び 1 つの間違いノートを共有することになります。

## 3. v0.4 から v0.5 以降へのアップグレード

現在、このアップグレードは v0.7 まで一気に進みます：下の手順に続いて 2.1 節と 1.1 節の手順が、**1 つ** のコピー `xexam-schema1-<YYYYmmdd-HHMMSS>.db` を書き出したうえで、**1 つ** のトランザクションで行われます。その後は `admin` / `admin` でログインし（2.3 節）、`admin` がすべてのデータを受け取ります。

### 3.1 データはどうなるか

v0.5 では、データベースに問題集、試験ごとの各問題の詳細、設定が加わりました（スキーマ v2）。変更は追加だけです。作り直されるものはなく、問題 id も 1 つも変わりません。詳しくは [database.md](database.md) の第 6 節を参照してください。

お使いのデータボリュームで新しいバージョンを**初めて起動**すると、バックエンドはリクエストを受け付ける前に次の処理を行います：

1. **バックアップ。** 現在のデータベースのコピーを、`xexam.db` と同じ場所の `backups/xexam-schema1-<YYYYmmdd-HHMMSS>.db` に書き出します（Docker では、ボリューム `xexam_data` 内の `/data/backups/`）。このコピーは通常のスキーマ 1 のデータベースで、v0.4 で開けます。既存のファイルを上書きすることはありません。**コピーを書き出せない場合**（ディスクがいっぱい、権限がないなど）、バックエンドは起動を中止し、データベースには手を付けません。理由はログに出ます。
2. **移行**（1 つのトランザクションで実行）：
   - 既存のデータはすべて **1 つの問題集**（「レガシー」問題集）になります。名前は、最後にインポートしたファイルの名前から `.xlsx` を除いたものです（一度もインポートしていなければ `Question bank`）。
   - **問題 id は変わりません。** そのため、問題ごとの統計、間違いノート、試験の履歴は、引き続きそれぞれの問題に結び付いています。
   - **試験記録は残り**、この問題集の記録になります。ただし、問題ごとの詳細はありません。v0.4 は回答内容を保存していなかったためです。詳細ページには得点が表示されますが、回答は表示されず、「受け直し」のボタンもありません。
   - インポート履歴も残り、この問題集のものになります。

2 回目以降の起動では、直すべきものがないかを読み取りだけで確認し、何も書き込みません。

ほかに気づく点：

- **画面は英語で始まります。** v0.4 は中国語でした。**Settings → Interface language**（日本語表示では **設定 → 表示言語**）か、ログインページで変更できます。この設定はデータベースに保存されるので、一度設定すれば、どのブラウザ・端末でも同じになります。
- テーマは、**設定** で選ぶまでシステムの設定（ライトまたはダーク）に従います。
- 問題の言語（試験ページの日本語・中国語・英語）は、これまでブラウザが記憶していました。新しいバージョンをブラウザで初めて開いたとき、サーバー側がまだ既定値（日本語）のままであれば、その選択がサーバーに移されます。
- ブラウザに保存されている未提出の試験はそのまま残り、続きから回答できます（そのブラウザで最初にログインした管理者のものになります）。
- データベースに残す記録の数が、60 件から、ユーザーごとに最新の 500 件に増えました。

### 3.2 アップグレード

`.env`、ポート、ボリュームは何も変わりません（[deployment.md](deployment.md) の第 6 節を参照）。v0.5.1 から変わったのは、`docker-compose.yml` のイメージの取得元だけです。`ghcr.io` ではなく Docker Hub（`docker.io/yuminspace/…`、公開、ログイン不要）から pull します。お使いの `docker-compose.yml` を新しいファイルに差し替えるか、その 2 つの `image:` の行を `docker.io/yuminspace/xexam-backend:latest` と `docker.io/yuminspace/xexam-frontend:latest` に変更してください。プロジェクト名とボリューム `xexam_data` は変わらないので、データはそのまま残ります。

```bash
# 1. ボリュームをバックアップ（先に停止する。バックアップファイルにはデータベース全体が入っているので、コミットしない）
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data-v04.tgz -C /data .

# 2. 新しい docker-compose.yml（Docker Hub のイメージ）を配置したうえで、現在のバージョンを pull して起動（down -v は使わない）
docker compose pull
docker compose up -d

# 3. アップグレードのメッセージとコピーのファイル名を確認
docker compose logs backend
```

ログには `Upgraded the database to schema 4. A copy of the previous version was saved first: /data/backups/xexam-schema1-20261110-140501.db (…)` のような行が出るはずです。このコピーはプログラム自身が書き出します。手順 1 の `.tgz` は、ボリュームの外に置く自分用の 2 つ目のコピーです。

ソースからビルドしている場合：リポジトリのルートで `git pull && docker compose -f docker/docker-compose.build.yml up -d --build`。compose ファイルは `docker/` に移りました。このコマンドの前に、リポジトリのルートにある `.env` を `docker/.env` に移動し（Compose はルートの `.env` を読まなくなりました）、その後のコマンド（`logs backend` など）にも `-f docker/docker-compose.build.yml` を付けてください。Docker を使わない場合、コピーはデータディレクトリ（`--data` または `XEXAM_DATA`）の中の `backups/` に書き出されます。

### 3.4 v0.4 へのロールバック

ロールバックとは、**移行前に書き出されたコピーを元に戻し**、v0.4 のイメージを実行することです。移行後に新しいバージョンで行ったことはすべて失われます：アカウント、新しい問題集、インポート、記録、設定。

```bash
# 1. 新しいバージョンを停止（down -v は使わない）
docker compose stop

# 2. コピーを探す。正常に停止していれば、/data に xexam.db-journal はなく、xexam.db-wal が残っていても空
docker run --rm -v xexam_data:/data alpine ls -l /data /data/backups

# 3. コピーを xexam.db として戻す（ファイル名は手順 2 で確認したものを使う。残っている -wal / -shm のファイルは先に削除する）
docker run --rm -v xexam_data:/data alpine sh -c 'rm -f /data/xexam.db-wal /data/xexam.db-shm && cp /data/backups/xexam-schema1-20261110-140501.db /data/xexam.db'

# 4. v0.4 は非公開の GHCR ミラーにしかない（Docker Hub は v0.5.1 から）。docker login ghcr.io を実行してから、docker-compose.yml の 2 つのイメージを次のように変更
#      image: ghcr.io/yumin-space/xexam-backend:v0.4
#      image: ghcr.io/yumin-space/xexam-frontend:v0.4
docker compose up -d
```

ソースからビルドしている場合は、代わりにタグをチェックアウトします：`git checkout v0.4 && docker compose -f docker-compose.build.yml up -d --build`（このタグでは compose ファイルはまだリポジトリのルートにあり、Compose は `.env` もルートから読みます。`docker/.env` がある場合は、先にリポジトリのルートへコピーしてください）。

手順 3 の代わりに、3.2 節で作った自分用の `.tgz` を復元してもかまいません（復元コマンドは [database.md](database.md) の第 5 節にあります）。中身は同じデータです。手順 4 はどちらの場合も必要です。

コピーを戻す代わりに、**移行済みのデータベースで v0.4 を実行しないでください**。v0.4 はこのファイルを開けますが、すべての問題集を 1 つとして扱います。次にインポートすると、ほかのすべての問題集の問題が出題停止になり、試験記録も 60 件に切り詰められ、アカウントのことも何も知りません。それでも実行してしまった場合は、次に新しいバージョンを起動したときに、v0.4 が追加した問題がレガシー問題集に組み込まれます（[database.md](database.md) の 6.6 節）。

あとで再びアップグレードするときは、新しい `docker-compose.yml`（Docker Hub のイメージ、タグ `:latest`）に戻して `docker compose pull && docker compose up -d` を実行します。移行がもう一度行われ、新しいコピーが書き出されます。

### 3.5 テスト済みの内容

合成データだけを使っています（`backend/tests/v05_banks_records_settings.rs`、`v06_users_and_sign_in.rs`、`db_golden.rs`）：

- `sample.db`（旧 Python 実装が書き出したデータベース）は、すべての問題 id、統計、試験記録、インポート履歴を保ったまま現在のスキーマに移行される。そのバックアップは引き続きスキーマ 1 を示し、元の行をそのまま保持している。
- スキーマ 1 のデータベースは、スキーマ 1 のバックアップを 1 つ書き出したうえで、一度に現在のスキーマになる。
- バックアップを書き出せない場合、データベースは移行されず、変更もされない。
- 移行済みのデータベースをもう一度開いても、ファイルは 1 バイトも変わらない。
- 古いバイナリが移行済みのファイルに書き込んだ行は、次の起動時にレガシー問題集に組み込まれる。
- 新規作成したデータベースと移行したデータベースは、同じ構造になる。

テストしていないもの：**ご自身の**データベースの移行。確実を期したい場合は、まずコピーで試してください（第 5 節の「コピーで新バージョンを試す」と同じやり方です）。

## 4. Python から Rust へ（v0.3）：原則

1. **原本には触れません。** まずバックアップを取り、コピーで試し、問題がないことを確認してから切り替えます。
2. **いつでも戻せました。** v0.4 までは、2 つの実装が同じファイル、同じスキーマを読み書きします（移行時に合成データで双方向の往復を予行演習しました。第 8 節を参照）。v0.5 からはスキーマに新しいテーブルと列が加わったため、新しいバージョンから戻すには、移行前に書き出されたコピーを元に戻します（3.4 節）。

## 7. Python から Rust へ：ロールバック

Python 版に戻すことができます。旧バージョンの compose ファイルはもうメインブランチにないため、タグから取り出します：

```bash
# 1. 新バージョンを停止（down -v は実行しない）
docker compose stop

# 2. 旧バージョンの compose ファイルを取り出して、旧バージョンを起動（非公開の GHCR から ghcr.io/yumin-space/xexam:latest を pull するので、先に docker login ghcr.io を実行します。バージョンを固定したい場合は :latest を :v0.2.2 に書き換えてください）
git show python-v0.2:docker-compose.yml > docker-compose.legacy.yml
docker compose -f docker-compose.legacy.yml up -d
```

旧 compose のイメージタグは `:latest` ですが、**`ghcr.io/yumin-space/xexam:latest` は今回のリリース以降更新されません**（新しいイメージは `xexam-frontend` / `xexam-backend` という 2 つの新しい名前を使っています）。そのため、最後の Python 版を指したままになります。念のため、明示的に `:v0.2.2` と書いてください。

**v0.3 または v0.4 から戻す場合**、旧バージョンは引き続き同じ `xexam_data` ボリュームを使い、データは失われません。これらのバージョンが書き込んだデータ（新しくインポートした問題、新しい成績）は、すべて旧バージョンで読めます。これらのバージョンはスキーマを変更せず、`journal_mode` も変更せず、テーブルや列を追加せず、`user_version` も設定せず、`-wal` / `-shm` ファイルも残さないからです。

**v0.5 以降から戻す場合**、スキーマには新しいテーブルと列が加わっています（v0.7 からはファイルも WAL モードです）。まず 3.4 節の手順 1〜3 のとおり、移行前に書き出されたスキーマ 1 のコピーを元に戻し、それから上記の方法で旧バージョンを起動してください。

データまでアップグレード前の状態に戻したい場合（たとえば、新バージョンがデータを壊した疑いがあるとき）：

```bash
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine sh -c 'rm -f /data/xexam.db-wal /data/xexam.db-shm && tar xzf /backup/xexam-data.tgz -C /data'
docker compose -f docker-compose.legacy.yml up -d
```

> リストアは、バックアップで `/data` を上書きします。バックアップの後に新バージョンで行った変更はすべて失われます。本当に必要だと確認できたときだけ実行してください。

Docker を使わないロールバック：`git checkout python-v0.2` を実行し、`python server.py` を起動します（Python 3.8 以上が必要です）。データディレクトリは同じ `xexam.db` を指すようにします。

## 8. Python から Rust へ：予行演習で確認したこと

移行時（Python コードがまだ残っていたとき）に次の項目を行いました。**すべて架空のデータだけを使い**、実際のデータベースを読み取ったり、出力したり、変更したりしたことは一度もありません。旧 Python をその場で実行する必要があるスクリプトは、旧コードとともに削除しました。結論は、コミット済みのスナップショットテストが引き続き守っています。

| 予行演習 | 方法 | 結果 | 現在それを守っているもの |
|---|---|---|---|
| 新旧の双方向往復 | 旧 Python でデータベースを作成 → バックアップ + `integrity_check` → Rust が**コピー**を読む（旧バージョンとバイト単位で同一）→ Rust が 2 つ目のワークブックをインポートして成績を記録 → 旧 Python が読み戻す（Rust と同一）→ 旧 Python がさらに書き込む → Rust が再び読む | 19 項目に合格（「原本の sha256 が前後で変わらない」ことを含む） | `db_golden.rs`：`sample.db`（旧実装が書き出したデータベース）はすべての行を保ったまま現在のスキーマに移行され、移行後のファイルは、その後に開いて、読み取って、閉じても 1 バイトも変わらない。新規作成したデータベースの `sqlite_master` は、旧実装のテキストにその後の追加分を加えたもの |
| ゴールデンレスポンスとの突き合わせ | 172 件の旧バージョンのレスポンスを新バックエンドと項目ごとに比較 | 説明のつかない差異は 0 件、23 件は登録済み | `api_golden.rs` が CI のたびに再生する |

## 11. v0.1 からのアップグレード

データベースのファイル名は v0.2 から `xexam.db` です。データディレクトリに他の `.db` ファイルがあって `xexam.db` がない場合は、バックエンドの起動ログで警告されます。そのファイルを `xexam.db` に改名してから起動し直してください（古いファイルは削除されず、読み取られもしません）。古い `progress.json` は起動のたびに 1 回チェックされ、データベースにまだ学習記録がなく、かつ移行済みでない場合にだけ移行します。移行は 1 回限りで、既存の記録は上書きしません。
