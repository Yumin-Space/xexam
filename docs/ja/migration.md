# 移行とロールバック

> この文書では、すべてのアップグレード手順を新しい順に説明します：
>
> - **v0.4 → v0.5**（第 1 節）：データベースはスキーマ v2 に自動で移行します。移行の前に、バックアップのコピーが書き出されます。
> - **Python 版 v0.2.x → Rust + TypeScript + Nginx 版（v0.3）**（第 2〜8 節）：このときはデータベースファイルもスキーマも変わっていません。切り替えは「プログラムの入れ替え」であって「データの引っ越し」ではありませんでした。判断の根拠：[migration-plan.md](../zh-CN/history/migration-plan.md)。リスク：[risk-assessment.md](../zh-CN/history/risk-assessment.md)。
> - **v0.1 → それ以降**（第 9 節）：データベースのファイル名について。

## 1. v0.4 から v0.5 へのアップグレード

### 1.1 データはどうなるか

v0.5 では、データベースに問題集、試験ごとの各問題の詳細、設定が加わります（スキーマ v2）。変更は追加だけです。作り直されるものはなく、問題 id も 1 つも変わりません。詳しくは [database.md](database.md) の第 6 節を参照してください。

お使いのデータボリュームで v0.5 を**初めて起動**すると、バックエンドはリクエストを受け付ける前に次の処理を行います：

1. **バックアップ。** 現在のデータベースのコピーを、`xexam.db` と同じ場所の `backups/xexam-schema1-<YYYYmmdd-HHMMSS>.db` に書き出します（Docker では、ボリューム `xexam_data` 内の `/data/backups/`）。このコピーは通常のスキーマ 1 のデータベースで、v0.4 で開けます。既存のファイルを上書きすることはありません。**コピーを書き出せない場合**（ディスクがいっぱい、権限がないなど）、バックエンドは起動を中止し、データベースには手を付けません。理由はログに出ます。
2. **移行**（1 つのトランザクションで実行）：
   - 既存のデータはすべて **1 つの問題集**（「レガシー」問題集）になります。名前は、最後にインポートしたファイルの名前から `.xlsx` を除いたものです（一度もインポートしていなければ `Question bank`）。
   - **問題 id は変わりません。** そのため、問題ごとの統計、間違いノート、試験の履歴は、引き続きそれぞれの問題に結び付いています。
   - **試験記録は残り**、この問題集の記録になります。ただし、問題ごとの詳細はありません。v0.4 は回答内容を保存していなかったためです。詳細ページには得点が表示されますが、回答は表示されず、「受け直し」のボタンもありません。
   - インポート履歴も残り、この問題集のものになります。

2 回目以降の起動では、直すべきものがないかを読み取りだけで確認し、何も書き込みません。

ほかに気づく点：

- **画面は英語で始まります。** v0.4 は中国語でした。**Settings → Interface language**（日本語表示では **画面設定 → 表示言語**）で変更できます。この設定はデータベースに保存されるので、一度設定すれば、どのブラウザ・端末でも同じになります。
- テーマは、**画面設定**で選ぶまでシステムの設定（ライトまたはダーク）に従います。
- 問題の言語（試験ページの日本語・中国語・英語）は、これまでブラウザが記憶していました。v0.5 をブラウザで初めて開いたとき、サーバー側がまだ既定値（日本語）のままであれば、その選択がサーバーに移されます。
- ブラウザに保存されている未提出の試験はそのまま残り、続きから回答できます。
- データベースに残す試験の数が、60 回分から最新の 500 回分に増えました。

### 1.2 アップグレード

`.env`、ポート、ボリュームは何も変わりません（[deployment.md](deployment.md) の第 6 節を参照）。v0.5.1 から変わったのは、`docker-compose.yml` のイメージの取得元だけです。`ghcr.io` ではなく Docker Hub（`docker.io/yuminspace/…`、公開、ログイン不要）から pull します。お使いの `docker-compose.yml` を新しいファイルに差し替えるか、その 2 つの `image:` の行を `docker.io/yuminspace/xexam-backend:latest` と `docker.io/yuminspace/xexam-frontend:latest` に変更してください。プロジェクト名とボリューム `xexam_data` は変わらないので、データはそのまま残ります。

```bash
# 1. ボリュームをバックアップ（先に停止する。バックアップファイルにはデータベース全体が入っているので、コミットしない）
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data-v04.tgz -C /data .

# 2. 新しい docker-compose.yml（Docker Hub のイメージ）を配置したうえで、v0.5 を pull して起動（down -v は使わない）
docker compose pull
docker compose up -d

# 3. アップグレードのメッセージとコピーのファイル名を確認
docker compose logs backend
```

ログには `Upgraded the database to schema 2. A copy of the previous version was saved first: /data/backups/xexam-schema1-20261110-140501.db (…)` のような行が出るはずです。このコピーはプログラム自身が書き出します。手順 1 の `.tgz` は、ボリュームの外に置く自分用の 2 つ目のコピーです。

ソースからビルドしている場合：リポジトリのルートで `git pull && docker compose -f docker/docker-compose.build.yml up -d --build`。compose ファイルは `docker/` に移りました。このコマンドの前に、リポジトリのルートにある `.env` を `docker/.env` に移動し（Compose はルートの `.env` を読まなくなりました）、その後のコマンド（`logs backend` など）にも `-f docker/docker-compose.build.yml` を付けてください。Docker を使わない場合、コピーはデータディレクトリ（`--data` または `XEXAM_DATA`）の中の `backups/` に書き出されます。

### 1.3 アップグレード後の確認

- [ ] `/api/info` の `version` が `0.6` で、`bankCount`（有効な問題の数）がアップグレード前と同じ。
- [ ] **問題集の管理**に問題集が 1 つだけあり、すべてのシートが含まれていて、問題数がアップグレード前と同じ。
- [ ] **学習記録**に以前の試験が並んでいる。また、**学習記録 → 間違えた問題の復習**の問題数が、以前の間違いノートの問題数と同じ。
- [ ] （任意）**既存を更新**を選び、その問題集を選んで、前回と同じ Excel ファイルをアップロードします。プレビューには、このファイルの問題がまったく同じで、取り込むものはないと表示されるはずです。確認したらキャンセルします。これで、問題 id が変わっていないことを確認できます。
- [ ] 数問解いて提出する。新しい記録には、各問題と自分の回答が表示される。

### 1.4 v0.4 へのロールバック

ロールバックとは、**移行前に書き出されたコピーを元に戻し**、v0.4 のイメージを実行することです。移行後に v0.5 で行ったことはすべて失われます：新しい問題集、インポート、試験記録、設定。

```bash
# 1. v0.5 を停止（down -v は使わない）
docker compose stop

# 2. コピーを探す。正常に停止していれば、/data に xexam.db-journal はない
docker run --rm -v xexam_data:/data alpine ls -l /data /data/backups

# 3. コピーを xexam.db として戻す（ファイル名は手順 2 で確認したものを使う）
docker run --rm -v xexam_data:/data alpine cp /data/backups/xexam-schema1-20261110-140501.db /data/xexam.db

# 4. v0.4 は非公開の GHCR ミラーにしかない（Docker Hub は v0.5.1 から）。docker login ghcr.io を実行してから、docker-compose.yml の 2 つのイメージを次のように変更
#      image: ghcr.io/yumin-space/xexam-backend:v0.4
#      image: ghcr.io/yumin-space/xexam-frontend:v0.4
docker compose up -d
```

ソースからビルドしている場合は、代わりにタグをチェックアウトします：`git checkout v0.4 && docker compose -f docker-compose.build.yml up -d --build`（このタグでは compose ファイルはまだリポジトリのルートにあり、Compose は `.env` もルートから読みます。`docker/.env` がある場合は、先にリポジトリのルートへコピーしてください）。

手順 3 の代わりに、第 1.2 節で作った自分用の `.tgz` を復元してもかまいません（復元コマンドは [database.md](database.md) の第 5 節にあります）。中身は同じデータです。手順 4 はどちらの場合も必要です。

コピーを戻す代わりに、**移行済みのデータベースで v0.4 を実行しないでください**。少なくとも、問題集が 2 つ以上あるときは避けてください。v0.4 はこのファイルを開けますが、すべての問題集を 1 つとして扱います。次にインポートすると、ほかのすべての問題集の問題が出題停止になり、試験記録も 60 回分に切り詰められます。それでも実行してしまった場合は、次に v0.5 を起動したときに、v0.4 が追加した問題がレガシー問題集に組み込まれます（[database.md](database.md) の第 6.2 節）。

あとで再びアップグレードするときは、新しい `docker-compose.yml`（Docker Hub のイメージ、タグ `:latest`）に戻して `docker compose pull && docker compose up -d` を実行します。移行がもう一度行われ、新しいコピーが書き出されます。

### 1.5 テスト済みの内容

合成データだけを使っています（`backend/tests/v05_banks_records_settings.rs` と `db_golden.rs`）：

- `sample.db`（旧 Python 実装が書き出したデータベース）は、すべての問題 id、統計、試験記録、インポート履歴を保ったままスキーマ v2 に移行される。そのバックアップは引き続きスキーマ 1 を示し、元の行をそのまま保持している。
- バックアップを書き出せない場合、データベースは移行されず、変更もされない。
- 移行済みのデータベースをもう一度開いても、ファイルは 1 バイトも変わらない。
- 古いバイナリがスキーマ v2 のファイルに書き込んだ行は、次の起動時にレガシー問題集に組み込まれる。
- 新規作成したデータベースと移行したデータベースは、同じ構造になる。

テストしていないもの：**ご自身の**データベースの移行。確実を期したい場合は、まずコピーで試してください（第 3 節の「コピーで新バージョンを試す」と同じやり方です）。

## 2. Python から Rust へ（v0.3）：原則

1. **原本には触れません。** まずバックアップを取り、コピーで試し、問題がないことを確認してから切り替えます。
2. **いつでも戻せました。** v0.4 までは、2 つの実装が同じファイル、同じスキーマを読み書きします（移行時に合成データで双方向の往復を予行演習しました。第 6 節を参照）。v0.5 からはスキーマに新しいテーブルと列が加わったため、v0.5 から戻すには、移行前に書き出されたコピーを元に戻します（第 1.4 節）。
3. **旧実装は失われていません。** 旧コードは Git タグ `python-v0.2` にあり、旧イメージ `ghcr.io/yumin-space/xexam:v0.2.2`（および `:v0.2`、`:v0.2.1`）も引き続き GHCR にあって（非公開なので、pull するには `docker login ghcr.io` が必要です。Docker Hub にはありません）、新しいパイプラインで上書きされることはありません。リポジトリのメインブランチに Python コードはもうありません。

## 3. Python から Rust へ：アップグレード前チェックリスト

順番に行ってください。どの手順も、実際のデータベースは変更しません。

- [ ] **データボリュームをバックアップ**（先に旧コンテナを停止）：

  ```bash
  docker compose stop
  docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data.tgz -C /data .
  docker compose start
  ```

  バックアップファイルにはデータベース全体が入っているため、**Git にコミットしないでください**（`.gitignore` は `*.tgz` を無視するよう設定済みです）。
- [ ] **バックアップを検証**：一時ディレクトリに展開し、`sqlite3 work/xexam.db "PRAGMA integrity_check"` が `ok` を出力することを確認します（コマンドは [database.md](database.md) の第 5 節を参照）。
- [ ] **コピーで新バージョンを試す**：展開した `xexam.db` を**空の一時ディレクトリ**に置き、名前付きボリュームは使わずに、そのディレクトリでバックエンドを起動します：

  ```bash
  cd backend && cargo build --release
  XEXAM_DATA=/tmp/xexam-trial ./target/release/xexam-backend serve --no-browser
  ```

  ブラウザで <http://localhost:8765> を開き、問題数、間違いノート、成績履歴が旧バージョンと一致していることを確認します。（v0.5 以降では、このときコピーもスキーマ v2 に移行され、一時ディレクトリの中に `backups/` が書き出されます。）**試し終わったら、この一時ディレクトリを削除してください。**
- [ ] **旧バージョンの数字を控える**：`/api/info` の `bankCount`、ホーム画面の総問題数、間違いノートの問題数。アップグレード後に 1 つずつ突き合わせます。
- [ ] **`.env` を確認**：`XEXAM_ALLOWED_HOSTS` / `XEXAM_BIND` などは旧バージョンの値をそのまま使えます。変数名は変わっていません。

## 4. Python から Rust へ：アップグレード

```bash
# 1. 旧バージョンを停止（down -v は実行しない）
docker compose stop

# 2. 古いコンテナを削除（コンテナだけを削除し、ボリュームは削除しない）。旧バージョンのサービスとコンテナはどちらも xexam という名前で、新バージョンは frontend / backend です。
#    削除しないと、旧コンテナが「孤児」としてプロジェクトに残り、そのポートマッピングが 8765 を占有したままになるため、新しい xexam-frontend がポートの競合で起動できません。
docker rm xexam

# 3. 新しい docker-compose.yml（サービスが 2 つになり、ログインなしで Docker Hub から pull します）に差し替え、pull して起動（同じボリューム xexam_data、同じポート）
docker compose pull
docker compose up -d

# 4. 2 つのコンテナが healthy かどうかを確認
docker compose ps
```

`docker rm xexam` が削除するのは**コンテナ**だけで、データボリューム `xexam_data` は削除されません（ボリュームの削除には `docker volume rm` か `down -v` が必要です。どちらも実行しないでください）。

Python 版から v0.5 へ直接アップグレードする場合も、第 1 節のスキーマ v2 への移行が行われ、バックアップのコピーが書き出されます。

アップグレード後の確認：

- [ ] `/api/info` の `version` がインストールしたバージョン（現在は `0.6`）で、`bankCount` がアップグレード前と同じ。
- [ ] 問題数、間違いノートの問題数、成績履歴がアップグレード前と同じ。
- [ ] 適当に数問解いて提出し、成績が履歴に表示される。
- [ ] （任意）同じ Excel ファイルをもう一度アップロードする（v0.5 以降は **既存を更新** を選び、1 つしかない問題集を指定します）：プレビューには追加・更新・出題停止の問題がなく（数が 0 のチップは表示されません）、このファイルの問題は現在の問題とまったく同じで取り込む必要はない、と表示されるはずです。これは、新旧のパーサーが同じ問題群に対して**同一の問題 id** を算出することの証明になります。ここで「出題停止 + 追加」が大量に出たら、**キャンセルして直ちにロールバック**してください（第 5 節）。

> ⚠️ 新旧バージョンのプロジェクト名（`xexam`）、ボリューム（`xexam_data`）、ポートはすべて同じなので、**同時に実行できません**。旧バージョンのコンテナ名は `xexam`、新バージョンは `xexam-frontend` と `xexam-backend` です。そのため、アップグレード時には上の手順 2 のように旧コンテナを削除する必要があります。

## 5. Python から Rust へ：ロールバック

Python 版に戻すことができます。旧バージョンの compose ファイルはもうメインブランチにないため、タグから取り出します：

```bash
# 1. 新バージョンを停止（down -v は実行しない）
docker compose stop

# 2. 旧バージョンの compose ファイルを取り出して、旧バージョンを起動（非公開の GHCR から ghcr.io/yumin-space/xexam:latest を pull するので、先に docker login ghcr.io を実行します。バージョンを固定したい場合は :latest を :v0.2.2 に書き換えてください）
git show python-v0.2:docker-compose.yml > docker-compose.legacy.yml
docker compose -f docker-compose.legacy.yml up -d
```

旧 compose のイメージタグは `:latest` ですが、**`ghcr.io/yumin-space/xexam:latest` は今回のリリース以降更新されません**（新しいイメージは `xexam-frontend` / `xexam-backend` という 2 つの新しい名前を使っています）。そのため、最後の Python 版を指したままになります。念のため、明示的に `:v0.2.2` と書いてください。

**v0.3 または v0.4 から戻す場合**、旧バージョンは引き続き同じ `xexam_data` ボリュームを使い、データは失われません。これらのバージョンが書き込んだデータ（新しくインポートした問題、新しい成績）は、すべて旧バージョンで読めます。これらのバージョンはスキーマを変更せず、`journal_mode` も変更せず、テーブルや列を追加せず、`user_version` も設定せず、`-wal` / `-shm` ファイルも残さないからです。

**v0.5 から戻す場合**、スキーマには新しいテーブルと列が加わっています。まず第 1.4 節の手順 1〜3 のとおり、移行前に書き出されたコピーを元に戻し、それから上記の方法で旧バージョンを起動してください。

データまでアップグレード前の状態に戻したい場合（たとえば、新バージョンがデータを壊した疑いがあるとき）：

```bash
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar xzf /backup/xexam-data.tgz -C /data
docker compose -f docker-compose.legacy.yml up -d
```

> リストアは、バックアップで `/data` を上書きします。バックアップの後に新バージョンで行った変更はすべて失われます。本当に必要だと確認できたときだけ実行してください。

Docker を使わないロールバック：`git checkout python-v0.2` を実行し、`python server.py` を起動します（Python 3.8 以上が必要です）。データディレクトリは同じ `xexam.db` を指すようにします。

## 6. Python から Rust へ：予行演習で確認したこと

移行時（Python コードがまだ残っていたとき）に次の項目を行いました。**すべて架空のデータだけを使い**、実際のデータベースを読み取ったり、出力したり、変更したりしたことは一度もありません。旧 Python をその場で実行する必要があるスクリプトは、旧コードとともに削除しました。結論は、コミット済みのスナップショットテストが引き続き守っています。

| 予行演習 | 方法 | 結果 | 現在それを守っているもの |
|---|---|---|---|
| 新旧の双方向往復 | 旧 Python でデータベースを作成 → バックアップ + `integrity_check` → Rust が**コピー**を読む（旧バージョンとバイト単位で同一）→ Rust が 2 つ目のワークブックをインポートして成績を記録 → 旧 Python が読み戻す（Rust と同一）→ 旧 Python がさらに書き込む → Rust が再び読む | 19 項目に合格（「原本の sha256 が前後で変わらない」ことを含む） | `db_golden.rs`：`sample.db`（旧実装が書き出したデータベース）はすべての行を保ったままスキーマ v2 に移行され、移行後のファイルは、その後に開いて、読み取って、閉じても 1 バイトも変わらない。新規作成したデータベースの `sqlite_master` は、旧実装のテキストに v2 での追加分を加えたもの |

## 7. Python から Rust へ：旧バージョンとの意図的な差異

理由付きの完全な表は [api.md](api.md) の第 5 節にあります。1 件ごとに `tests/baseline/golden/allowed_differences_rust.json` と `allowed_probe_differences_rust.json` に登録されており、登録のない差異があるとテストが失敗します。利用者から見えるものは次のとおりです：

| 項目 | 変更点 |
|---|---|
| アーキテクチャ | 1 つのコンテナが 2 つ（nginx + backend）になりました。イメージ名は `xexam-frontend` / `xexam-backend`。`XEXAM_BIND` は Nginx を指すようになりました |
| より厳格なアップロード検査 | どの文字コード / 拡張子であっても DOCTYPE を拒否。重複した ZIP エントリ名を拒否。エントリ数、XML の深さ、ノード数に上限あり |
| エラーメッセージ | 残りの中国語は一字一句そのまま保持。以前はライブラリの例外テキストをそのまま返していた 2 か所を、固定の中国語メッセージに変更 |
| 採点 | 引き続きブラウザ内で行い、サーバー側には移していません（仕様では移すことを勧めていますが、ここでは意図的に移していません。理由は [migration-plan.md](../zh-CN/history/migration-plan.md) の Q3 を参照） |
| iPhone | iOS 15.4 以上が必要（ビルドターゲット `safari15`） |
| 提供しなくなったもの | バックエンドによる静的ファイルの配信（Nginx が配信します）、`Server` レスポンスヘッダー |

v0.5 での API の変更点は、[api.md](api.md) の第 5 節にある「v0.5 での変更」の項に一覧があります。

## 8. Python から Rust へ：検証していないもの

- 本物の Cloudflare Tunnel / Access、iPhone の実機、本物の ARM ハードウェア上での実行（arm64 は QEMU 上でビルドして起動を確認しただけです）。
- **ご自身の実データベース**のコピーを使った予行演習：こちらでは入手しておらず、読み取るべきでもありません。第 3 節に従って、ご自身のマシンで行ってください。

## 9. v0.1 からのアップグレード

データベースのファイル名は v0.2 から `xexam.db` です。データディレクトリに他の `.db` ファイルがあって `xexam.db` がない場合は、バックエンドの起動ログで警告されます。そのファイルを `xexam.db` に改名してから起動し直してください（古いファイルは削除されず、読み取られもしません）。古い `progress.json` は起動のたびに 1 回チェックされ、データベースにまだ学習記録がなく、かつ移行済みでない場合にだけ移行します。移行は 1 回限りで、既存の記録は上書きしません。
