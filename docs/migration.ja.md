# 移行とロールバック

> Python 版（v0.2.x）から Rust + TypeScript + Nginx 版（v0.3）への切り替えです。**データベースファイルもスキーマも 1 文字も変わっていません**。そのため、切り替えは「プログラムの入れ替え」であって「データの引っ越し」ではありません。
> 判断の根拠：[migration-plan.md](migration-plan.md)。リスク：[risk-assessment.md](risk-assessment.md)。

## 1. 原則

1. **原本には触れません。** まずバックアップを取り、コピーで試し、問題がないことを確認してから切り替えます。
2. **いつでも戻せます。** 2 つの実装は同じファイル、同じスキーマを読み書きします（移行時に合成データで双方向の往復を予行演習しました。§5 を参照）。
3. **旧実装は失われていません。** 旧コードは Git タグ `python-v0.2` にあり、旧イメージ `ghcr.io/yumin-space/xexam:v0.2.2`（および `:v0.2`、`:v0.2.1`）も引き続き GHCR にあって、新しいパイプラインで上書きされることはありません。リポジトリのメインブランチに Python コードはもうありません。

## 2. アップグレード前チェックリスト

順番に行ってください。どの手順も、実際のデータベースは変更しません。

- [ ] **データボリュームをバックアップ**（先に旧コンテナを停止）：

  ```bash
  docker compose stop
  docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar czf /backup/xexam-data.tgz -C /data .
  docker compose start
  ```

  バックアップファイルにはデータベース全体が入っているため、**Git にコミットしないでください**（`.gitignore` は `*.tgz` を無視するよう設定済みです）。
- [ ] **バックアップを検証**：一時ディレクトリに展開し、`sqlite3 work/xexam.db "PRAGMA integrity_check"` が `ok` を出力することを確認します（コマンドは [database.ja.md](database.ja.md) の第 5 節を参照）。
- [ ] **コピーで新バージョンを試す**：展開した `xexam.db` を**空の一時ディレクトリ**に置き、名前付きボリュームは使わずに、そのディレクトリでバックエンドを起動します：

  ```bash
  cd backend && cargo build --release
  XEXAM_DATA=/tmp/xexam-trial ./target/release/xexam-backend serve --no-browser
  ```

  ブラウザで <http://localhost:8765> を開き、問題数、誤答ノート、成績履歴が旧バージョンと一致していることを確認します。**試し終わったら、この一時ディレクトリを削除してください。**
- [ ] **旧バージョンの数字を控える**：`/api/info` の `bankCount`、ホーム画面の総問題数、誤答の問題数。アップグレード後に 1 つずつ突き合わせます。
- [ ] **`.env` を確認**：`XEXAM_ALLOWED_HOSTS` / `XEXAM_BIND` などは旧バージョンの値をそのまま使えます。変数名は変わっていません。

## 3. アップグレード

```bash
# 1. 旧バージョンを停止（down -v は実行しない）
docker compose stop

# 2. 古いコンテナを削除（コンテナだけを削除し、ボリュームは削除しない）。旧バージョンのサービスとコンテナはどちらも xexam という名前で、
#    新バージョンは frontend / backend です。削除しないと、旧コンテナが「孤児」としてプロジェクトに残り、
#    そのポートマッピングが 8765 を占有したままになるため、新しい xexam-frontend がポートの競合で起動できません。
docker rm xexam

# 3. 新しい docker-compose.yml（サービスが 2 つになります）に差し替え、pull して起動（同じボリューム xexam_data、同じポート）
docker compose pull
docker compose up -d

# 4. 2 つのコンテナが healthy かどうかを確認
docker compose ps
```

`docker rm xexam` が削除するのは**コンテナ**だけで、データボリューム `xexam_data` は削除されません（ボリュームの削除には `docker volume rm` か `down -v` が必要です。実行しないでください）。

アップグレード後の確認：

- [ ] `/api/info` の `version` が `0.4` で、`bankCount` がアップグレード前と同じ。
- [ ] ホーム画面の問題数、誤答ノートの問題数、成績履歴がアップグレード前と同じ。
- [ ] 適当に数問解いて提出し、成績が履歴に表示される。
- [ ] （任意）同じ Excel をもう一度アップロードする：プレビューに `新增 0、更新 0、下架 0`（追加 0、更新 0、無効化 0）と表示されるはずです。これは、新旧のパーサーが同じ問題群に対して**同一の問題 id** を算出することの証明になります。ここで大量の「無効化 + 追加」が出たら、**直ちにロールバック**してください（§4）。

> ⚠️ 新旧バージョンのプロジェクト名（`xexam`）、ボリューム（`xexam_data`）、ポートはすべて同じなので、**同時に実行できません**。旧バージョンのコンテナ名は `xexam`、新バージョンは `xexam-frontend` と `xexam-backend` です。そのため、アップグレード時には上の手順 2 のように旧コンテナを削除する必要があります。

## 4. ロールバック

いつでも Python 版に戻せます。**データは失われません**。旧バージョンの compose ファイルはもうメインブランチにないため、タグから取り出します：

```bash
# 1. 新バージョンを停止（down -v は実行しない）
docker compose stop

# 2. 旧バージョンの compose ファイルを取り出して、旧バージョンを起動（ghcr.io/yumin-space/xexam:latest を pull します。バージョンを固定したい場合は :latest を :v0.2.2 に書き換えてください）
git show python-v0.2:docker-compose.yml > docker-compose.legacy.yml
docker compose -f docker-compose.legacy.yml up -d
```

旧 compose のイメージタグは `:latest` ですが、**`ghcr.io/yumin-space/xexam:latest` は今回のリリース以降更新されません**（新しいイメージは `xexam-frontend` / `xexam-backend` という 2 つの新しい名前を使っています）。そのため、最後の Python 版を指したままになります。念のため、明示的に `:v0.2.2` と書いてください。

旧バージョンは引き続き同じ `xexam_data` ボリュームを使います。新バージョンが書き込んだデータ（新しくインポートした問題、新しい成績）は旧バージョンでも読めます。新しいバックエンドはスキーマを変更せず、`journal_mode` も変更せず、テーブルや列を追加せず、`user_version` も設定せず、`-wal` / `-shm` ファイルも残さないからです。

データまでアップグレード前の状態に戻したい場合（たとえば新バージョンが書き込んだデータが壊れた疑いがあるとき）：

```bash
docker compose stop
docker run --rm -v xexam_data:/data -v "$PWD:/backup" alpine tar xzf /backup/xexam-data.tgz -C /data
docker compose -f docker-compose.legacy.yml up -d
```

> リストアは、バックアップで `/data` を上書きします。その後に新バージョンで行った変更はすべて失われます。本当に必要だと確認できたときだけ実行してください。

Docker を使わないロールバック：`git checkout python-v0.2` を実行し、`python server.py` を起動します（Python 3.8 以上が必要です）。データディレクトリは同じ `xexam.db` を指すようにします。

## 5. 予行演習で確認したこと

移行時（Python コードがまだ残っていたとき）に次の項目を行いました。**すべて架空のデータだけを使い**、実際のデータベースを読み取ったり、出力したり、変更したりしたことは一度もありません。旧 Python をその場で実行する必要があるスクリプトは、旧コードとともに削除しました。結論は、コミット済みのスナップショットテストが引き続き守っています。

| 予行演習 | 方法 | 結果 | 現在それを守っているもの |
|---|---|---|---|
| 新旧の双方向往復 | 旧 Python でデータベースを作成 → バックアップ + `integrity_check` → Rust が**コピー**を読む（旧バージョンとバイト単位で同一）→ Rust が 2 つ目のワークブックをインポートして成績を記録 → 旧 Python が読み戻す（Rust と同一）→ 旧 Python がさらに書き込む → Rust が再び読む | 19 項目に合格（「原本の sha256 が前後で変わらない」ことを含む） | `db_golden.rs`：`sample.db`（旧実装が書き出したデータベース）は、開いて、読み取って、閉じても 1 バイトも変わらない。新規作成したデータベースの `sqlite_master` は旧実装と一字一句同じ |
| ゴールデンレスポンスとの突き合わせ | 172 件の旧バージョンのレスポンスを新バックエンドと項目ごとに比較 | 説明のつかない差異は 0 件、23 件は登録済み | `api_golden.rs` が CI のたびに再生する |
| セキュリティプローブ | 340 件の悪意あるリクエストを旧バージョンと新バージョンの両方に送信、設定は 3 種類 | 説明のつかない差異は 0 件、51 件は登録済み（多くは新バージョンのほうが厳格） | プローブのスクリプトは削除済み。ガードとアップロード検査は `api_*.rs`、`parser_hardening.rs`、`nginx_check.py` がテストしている |
| パーサーの差分比較 | 49 個の合成ワークブックについて、旧パーサーと Rust パーサーの出力を項目ごとに比較。85 件の問題 id ベクトル | すべて一致 | `parser_golden.rs`、`id_vectors.rs` が CI のたびに実行される |
| 全スタック | `tests/integration/stack_check.py`：スタックを起動し、アップロード / インポート / 提出を行い、コンテナを削除しても同じボリュームで再構築するとデータが残っていること、`docker stop` の所要時間、非 root を確認 | 34 項目に合格 | CI のたびに実行される |

## 6. 旧バージョンとの意図的な差異

理由付きの完全な表は [api.ja.md](api.ja.md) の第 5 節にあります。1 件ごとに `tests/baseline/golden/allowed_differences_rust.json` と `allowed_probe_differences_rust.json` に登録されており、登録のない差異があるとテストが失敗します。利用者から見えるものは次のとおりです：

| 項目 | 変更点 |
|---|---|
| アーキテクチャ | 1 つのコンテナが 2 つ（nginx + backend）になりました。イメージ名は `xexam-frontend` / `xexam-backend`。`XEXAM_BIND` は Nginx を指すようになりました |
| より厳格なアップロード検査 | どの文字コード / 拡張子であっても DOCTYPE を拒否。重複した ZIP エントリ名を拒否。エントリ数、XML の深さ、ノード数に上限あり |
| エラーメッセージ | 残りの中国語は一字一句そのまま保持。以前はライブラリの例外テキストをそのまま返していた 2 か所を、固定の中国語メッセージに変更 |
| 採点 | 引き続きブラウザ内で行い、サーバー側には移していません（仕様では移すことを勧めていますが、ここでは意図的に移していません。理由は [migration-plan.md](migration-plan.md) の Q3 を参照） |
| iPhone | iOS 15.4 以上が必要（ビルドターゲット `safari15`） |
| 提供しなくなったもの | バックエンドによる静的ファイルの配信（Nginx が配信します）、`Server` レスポンスヘッダー |

## 7. v0.1 からのアップグレードに関する注意

データベースのファイル名は v0.2 から `xexam.db` です。データディレクトリに他の `.db` ファイルがあって `xexam.db` がない場合は、バックエンドの起動ログでお知らせします。そのファイルを `xexam.db` に改名してから起動し直せば大丈夫です（古いファイルは削除されず、読み取られもしません）。古い `progress.json` は起動のたびに 1 回チェックされ、データベースにまだ学習記録がなく、かつ移行済みでない場合にだけ移行します。移行は 1 回限りで、既存の記録は上書きしません。

## 8. 検証していないもの

- 本物の Cloudflare Tunnel / Access、iPhone の実機、本物の ARM ハードウェア上での実行（arm64 は QEMU 上でビルドして起動を確認しただけです）。
- **ご自身の実データベース**のコピーを使った予行演習：こちらでは入手しておらず、読み取るべきでもありません。§2 に従って、ご自身のマシンで一度行ってください。
